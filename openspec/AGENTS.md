# OpenSpec — конвенции в этом репозитории

Spec-driven разработка: сначала предложение и спека, потом код. Здесь — минимум,
которого достаточно для работы.

## Структура

```
openspec/
  project.md              — контекст проекта (стек, контракты, конвенции)
  AGENTS.md               — этот файл
  specs/                  — действующая правда: что система уже умеет
    <capability>/spec.md
  changes/                — незавершённые изменения
    <change-id>/
      proposal.md         — Why / What Changes / Impact
      tasks.md            — упорядоченный чек-лист работ
      design.md           — только когда есть архитектурный выбор
      specs/<capability>/spec.md   — дельта к спеке
```

`change-id` — глагол в начале, kebab-case: `add-monorepo-skeleton`,
`fix-token-budget`. Один change = одна связная поставка.

## Формат дельты спеки

```markdown
## ADDED Requirements

### Requirement: Название требования
Система SHALL <проверяемое утверждение>.

#### Scenario: Название сценария
- **WHEN** <условие>
- **THEN** <ожидаемый результат>
```

Заголовки блоков — только `## ADDED Requirements`, `## MODIFIED Requirements`,
`## REMOVED Requirements`. У каждого требования — минимум один `#### Scenario:`.
В `MODIFIED` требование приводится целиком в новой редакции, а не диффом.

## Жизненный цикл

1. `changes/<id>/` создан, предложение обсуждено → работа начинается.
2. Задачи в `tasks.md` отмечаются `- [x]` по мере выполнения.
3. Когда изменение задеплоено — дельты переносятся в `openspec/specs/<capability>/`,
   папка change архивируется.

## CLI

`openspec` в проекте не установлен. Когда появится:

```bash
openspec list                      # активные changes
openspec validate <id> --strict    # проверка формата
```

До этого формат поддерживаем руками — он рассчитан на то, чтобы `validate --strict`
прошёл без правок.

## Правила

- Минимальная реализация, которая закрывает требование.
- Не расширять скоуп внутри change: нашли смежную проблему — новый change.
- Каждая задача в `tasks.md` проверяемая: тест, запрос или ручной сценарий.
- Ссылаться на доказательства: `файл:строка` в коде, раздел в `docks/`.

## Оговорка про сроки

До финала хакатона четыре дня. Через OpenSpec ведём **только крупные блоки**
(каркас, ядро, агент, фронт). Мелкие правки — мимо, иначе церемония съест время,
которого нет.
