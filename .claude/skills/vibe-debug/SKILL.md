# Vibe Debug

`vibe-debug` — рабочий процесс визуального и функционального ревью через
коммент-превью. Оверлей накладывается на страницу в рантайме; исходники им не
меняются. Комментарии хранятся как структурированные данные и становятся
задачами на код только после явной просьбы пользователя.

## Состояние в этом репозитории · заглушка

`tt_hack` — репозиторий документов кейса. Фронтенда пока нет, поэтому здесь
только каркас:

- `scripts/vibe_debug_server.py` — статический сервер + review API
  (`/__review__/*`), stdlib, без зависимостей. Порт из проекта `lapki`.
- `schemas/vibe-debug-comment.schema.json` — единственная схема DBG-записи.
- `preview/` — то, что отдаёт сервер: страница-заглушка и минимальный оверлей
  `assets/vibe-debug.js` + `assets/vibe-debug.css` (ставит пины, шлёт
  комментарии, меняет статусы). Режимов dev/art, рисования и вложений нет.
- `docs/VIBE-DEBUG.md` — как запускать и куда деплоить.

Когда появится настоящий UI: положить его в `preview/` (или задать
`VIBE_DEBUG_ROOT`) и подключить `vibe-debug.css` / `vibe-debug.js` на каждой
странице.

## Поднять превью

Основной контур — общий сервер команды (Nginx Basic Auth + systemd,
`deploy/`, см. `docs/VIBE-DEBUG.md`). Комментарии там общие и переживают
перезапуск. Локальный запуск — только для отладки самого оверлея.

1. Проверить, жив ли общий сервер: `curl -sf <preview-host>/__review__/comments`.
   Жив — не плодить второй, вернуть существующий URL и маршрут.
2. Локально, если нужно: `python3 scripts/vibe_debug_server.py`
   (порт — `VIBE_DEBUG_PORT`, корень статики — `VIBE_DEBUG_ROOT`,
   данные — `VIBE_DEBUG_DATA`).
3. Сообщить точный маршрут запрошенной страницы. Для всего сайта — корень.
4. Локальные комментарии лежат в `.vibe-debug/comments.json` (в git не коммитятся);
   на сервере — в каталоге из `VIBE_DEBUG_DATA` вне репозитория.

## Разобрать комментарии (triage)

Шаг между комментарием и кодом. Запускать, когда просят разобрать очередь.
Продуктовые файлы при этом не трогать.

1. Снять read-only снимок очереди (`GET /__review__/comments`).
2. По каждому замечанию: классифицировать
   (`content` / `ux` / `scope` / `question` / `bug`), написать, что понятно и
   что нет, назвать затронутые файлы, набросать промпт исполнителю.
3. Строку «Решение:» оставить пустой — её пишет человек.
4. Сложить карточки в `docs/review/<дата>-<область>.md`.
5. Отчитаться: файл карточек, счётчик по классам, всё, что не удалось
   классифицировать без ответа.

## Применить комментарии

Только когда пользователь говорит применить / закрыть / починить, **и** в
карточке есть строка «Решение:» от человека.

1. Перечитать карточку и исходную запись. Расходятся — остановиться и спросить.
2. Перевести комментарий в `in_progress` через `POST /__review__/comments/status`.
3. Внести минимальную связную правку. Пояснительные комментарии в коде не добавлять.
4. Проверить затронутый маршрут локально на 375 и 1440.
5. `resolved` — только когда правка видна в том же превью; `wont_fix` — с
   причиной для отклонённых.
6. Отчитаться: изменённые файлы, ID комментариев, URL превью, проверки,
   нерешённые риски.

## Схема комментария

Единственная схема — `schemas/vibe-debug-comment.schema.json`, её пишет
`normalize_comment()` в `scripts/vibe_debug_server.py`. Менять схему — значит
менять сервер и файл схемы одним коммитом. Записи, созданные до текущей схемы,
задним числом не переписываются.

## Жизненный цикл

`new` → `approved` → `in_progress` → `resolved`; терминальный отказ —
`wont_fix` с причиной. Комментарий — это вход, а не задача. Шаг одобрения
человеком не пропускать: карточку пишет агент, строку «Решение:» — только человек.

## Аутентификация

Локальное превью — без аутентификации. Тест и прод — за Nginx Basic Auth.
Логины/пароли живут только на сервере или в окружении деплоя, в репозитории —
никогда. Разрешённые ревьюеры задаются на сервере.

## Обязательный отчёт

Каждый вызов заканчивается компактным отчётом: цель и URL; действие (поднял,
сроутил, обработал, заблокирован); изменённые файлы и закрытые ID; проверки;
ветка и коммит; нерешённые вопросы и риски.
