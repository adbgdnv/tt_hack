# Implementation Plan: Сравнение контрагентов

**Branch**: `013-counterparty-comparison` | **Date**: 2026-09-05 | **Spec**: [spec.md](spec.md)

## Summary

**Ядро.** `core/compare.py` перестаёт быть заглушкой: `compare()` собирает
по каждой записи вердикт из уже посчитанных триггеров и разделов отчёта
и возвращает список **от чистого к спорному**. Рядом — `summary()`, который
складывает вывод словами: кто выглядит чище и с кем осторожнее.

**Ручка.** `POST /compare` принимает список ИНН и отдаёт вердикты и вывод.
Модель не участвует: всё считается кодом, поэтому экран открывается сразу
и переживает недоступность провайдера.

**Интерфейс.** Шапка получает два режима, появляется экран сравнения: пул
чипами, вывод сверху, карточки в порядке от чистого к спорному.

## Technical Context

**Language/Version**: Python 3.12 (ядро, API), TypeScript + React (интерфейс)

**Primary Dependencies**: без новых

**Storage**: нет. Пул живёт в состоянии страницы, как переписка

**Testing**: pytest на ядре — порядок, вывод словами, отсутствие балла,
краевые случаи (ИП, пул из одного, ничья). Интерфейс — руками по `quickstart.md`

**Target Platform**: тот же контейнер

**Project Type**: web

**Performance Goals**: экран строится без обращения к модели. Десять компаний
из набора читаются витриной за один проход

**Constraints**: ни балла, ни порядкового номера в выдаче ручки — то, чего нет
в контракте, невозможно случайно нарисовать

**Scale/Scope**: 200 компаний в наборе, пул до десяти

## Constitution Check

| Принцип | Как соблюдается |
|---|---|
| **I. Спека первична** | спека и замеры написаны до кода, вариант экрана выбран пользователем по холсту |
| **II. Ядро не знает протоколов** | `compare()` и `summary()` — чистые функции от записей; ручка тонкая обёртка |
| **III. Минимальная реализация** | ни одного нового правила: вердикт складывается из уже посчитанных триггеров и состояний разделов |
| **IV. Агент обращает внимание, а не выносит вердикт** | формулировки те же, что в блоке «Что не сходится»: «обратить внимание», а не «не работать» |
| **IV. Отсутствие данных — ответ** | пробелы в данных выводятся отдельным полем и показываются рядом с выводом |
| **V. Отбор полей** | не затрагивается: модель в сравнении не участвует |

Отклонений нет.

## Project Structure

```
src/core/
  compare.py             перестаёт быть заглушкой: Verdict, compare, summary, shortlist

src/api/
  main.py                правка: POST /compare

src/web/src/
  App.tsx                правка: два режима, пул, экран сравнения
  api.ts                 правка: запрос сравнения
  types.ts               правка: вердикт и вывод
  components/
    ComparePool.tsx      ← новый: пул чипами и добавление по ИНН
    CompareVerdicts.tsx  ← новый: вывод сверху и карточки по порядку
  styles.css             правка: экран сравнения, вкладки в шапке

tests/
  test_compare.py        ← новый
```

**Structure Decision**: вывод собирается в ядре, а не в интерфейсе. Он опирается
на те же триггеры, что и отчёт, и должен звучать одинаково в вебе, в MCP
и в ответе агента — три отрисовки одного вывода разошлись бы, как когда-то
разошлись `run` и `run_stream`.

**Почему у `Verdict` появляется `level`, а балл не появляется.** Интерфейсу
нужен цвет точки, и выводить его из русской фразы значит завести разбор строк.
`level` — то же трёхсостояние, что у разделов отчёта, а не оценка: он не
складывается, не сравнивается числом и не показывается пользователю.

**Почему порядок задаётся в ядре, а не сортировкой на клиенте.** Порядок — часть
вывода: «сверху тот, к кому меньше вопросов» — утверждение о компаниях, а не
украшение таблицы. Клиент, отсортировавший иначе, сделал бы вывод неверным.
