# Модель данных

## Trigger — сработавшее противоречие

| Поле | Что это |
|---|---|
| `key` | устойчивое имя, латиницей: `status_note`, `lights_silent`, … |
| `title` | как называется на экране: «Статус с оговоркой» |
| `explanation` | одна фраза, что именно противоречит чему |
| `evidence` | значения, из которых сложилось, уже отформатированные |
| `section` | ключ раздела отчёта, где это можно проверить |
| `fields` | пути внутри данных — для словаря и для проверки, не для экрана |
| `weight` | значимость, задаёт порядок по умолчанию |
| `tags` | к какому вопросу относится: `финансы`, `суды`, `надёжность`, `данные` |

`evidence` хранит **готовые к показу значения**, а не сырые числа: правило
форматирования сумм уже живёт в отчёте, и второе его место разойдётся с первым.

`fields` не показывается пользователю никогда — это то, чем триггер проверяется,
и вход в словарь.

## FieldEntry — статья словаря

| Поле | Что это |
|---|---|
| `path` | путь внутри данных, `finReports[].common.proceeds` |
| `label` | как называть словами: «Выручка за год» |
| `description` | описание из спецификации кейсодателя, дословно |
| `origin` | `spec` — из официальной спецификации, `own` — написано нами |
| `section` | раздел отчёта |
| `tags` | раздел спецификации плюс наши: на какой вопрос отвечает |
| `filled` | у скольких компаний из 200 заполнено |

`origin` обязателен: пользователь и мы должны различать, где формулировка
кейсодателя, а где наша. `filled` — чтобы не строить правило на поле,
заполненном у трёх компаний, не заметив этого.

## Intent — намерение вопроса

| Поле | Что это |
|---|---|
| `key` | `deferral`, `prepayment`, `lights_doubt`, `general` |
| `tags` | какие теги триггеров поднимаются наверх |
| `patterns` | слова, по которым намерение узнаётся |

Намерение меняет **порядок**, не состав. Триггер, не совпавший по тегам,
опускается ниже, но остаётся: спросивший про выручку не должен пропустить
банкротство.

Неузнанный вопрос даёт `general` — порядок по `weight`, как без вопроса.
