# Feature Specification: Триггеры из данных и словарь полей

**Feature Branch**: `009-risk-triggers`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "давай тогда займись изучением данных и получением триггеров из них - юзер ещё задаст query - поэтому его можно тоже учитывать при отфильтровывании рисков" + "давай ещё параллельно сделаем улучшение данных — у нас было текстовое описание данных, надо навешать на них какие-то теги на разные данные, чтобы теоретически мы ещё смогли добавить раг и подкладывать в контекст нужную информацию по тегам"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Сразу видно, на что смотреть (Priority: P1)

Пользователь открывает карточку контрагента и, не читая восемь разделов, видит
короткий список того, на что стоит обратить внимание именно у этой компании.
Не пересказ риск-кодов, которые источник и так подсвечивает, а **противоречия
между разными частями отчёта**, которых не видно ни в одном поле по отдельности:
светофоры зелёные, а компания в банкротстве; выручка растёт, а прибыль падает;
отчётность двухлетней давности.

**Why this priority**: Это и есть заявленная задача продукта — переложить разбор
отчёта с человека. Сейчас пользователь читает восемь карточек и складывает вывод
сам. Замерено: 62% компаний не дают ни одного такого противоречия, то есть
для большинства список будет пустым — и это тоже ответ, причём быстрый.

**Independent Test**: Открыть ООО «МАКСМАРКЕТ» (ИНН 5032257375) и увидеть, что
статус помечен оговоркой о банкротстве, а оба светофора при этом зелёные —
не открывая ни одного раздела.

**Acceptance Scenarios**:

1. **Given** компания, у которой оба светофора зелёные и при этом 2,6 млрд ₽
   исков в роли ответчика, **When** пользователь открывает её карточку,
   **Then** он видит отдельным пунктом, что светофоры этого не покрывают,
   с указанием обеих величин и раздела, где их проверить.
2. **Given** компания без единого сработавшего триггера, **When** пользователь
   открывает её карточку, **Then** он видит явное «противоречий в данных нет»,
   а не пустое место.
3. **Given** сработавший триггер, **When** пользователь на него смотрит,
   **Then** названы поля, из которых он сложился, и раздел отчёта, где эти
   значения видно.

---

### User Story 2 - Вопрос пользователя меняет порядок (Priority: P2)

Пользователь спрашивает своими словами — «дать ли отсрочку на 60 дней»,
«стоит ли платить аванс 40%», «почему светофор зелёный, если компания смущает».
Список того, на что смотреть, перестраивается под вопрос: для отсрочки вперёд
выходят платёжеспособность и взыскания, для аванса — способность вернуть деньги,
для сомнения в светофоре — ровно то, чего светофор не покрывает.

**Why this priority**: Ситуации взяты из `docs/roles_situations.md`, они уже
отобраны и подтверждены кейсодателем. Без этого продукт даёт один ответ на все
вопросы. Работает поверх первой истории и без неё бессмысленен.

**Independent Test**: Задать по одной и той же компании два разных вопроса
и получить разный порядок пунктов при одинаковом их составе.

**Acceptance Scenarios**:

1. **Given** компания с сработавшими триггерами о финансах и о судах,
   **When** пользователь спрашивает про отсрочку платежа, **Then** финансовые
   пункты стоят выше судебных.
2. **Given** тот же контрагент, **When** пользователь спрашивает «почему
   светофор зелёный», **Then** первым идёт пункт о том, чего светофоры
   не покрывают.
3. **Given** сработавший триггер, не связанный с вопросом, **When** пользователь
   задаёт узкий вопрос, **Then** этот триггер **остаётся виден**, но ниже —
   он не скрывается.

---

### User Story 3 - Экран говорит по-русски, а не путями JSON (Priority: P3)

Под графиками и в объяснениях агента вместо `finReports[].assets.currentAssets.
{stocks,receivables,bankroll}` пользователь видит «Запасы, дебиторская
задолженность и денежные средства по бухгалтерской отчётности».

**Why this priority**: Кейсодатель отдельным пунктом просил «вычистить UI
от нейрослопа, от технических терминов». Сейчас путь JSON показан пользователю
буквально. Тот же словарь одновременно готовит почву для будущего подбора
контекста по тегам.

**Independent Test**: Открыть детальный вид раздела «Финансы» и убедиться,
что ни одна подпись источника не содержит квадратных скобок и точек пути.

**Acceptance Scenarios**:

1. **Given** график, построенный из полей отчётности, **When** пользователь
   открывает детальный вид, **Then** источник назван словами, а не путём.
2. **Given** поле, которого нет в официальной спецификации кейсодателя,
   **When** оно попадает на экран, **Then** видно, что описание наше,
   а не из спецификации.

---

### Edge Cases

- **Триггеров сработало больше, чем помещается.** Замерено: максимум 5 на
  компанию, три и более — у 11 из 200. Порядок задаёт значимость, а не случай.
- **Данных для триггера нет вовсе.** Отсутствие отчётности — это не «всё
  хорошо». Триггер «отчётности нет» существует отдельно и срабатывает у 14
  компаний из 200, не считая ИП, у которых её не бывает по устройству формы.
- **Вопрос пользователя не про эту компанию** или не разобран — порядок
  остаётся по умолчанию, ничего не скрывается.
- **Поле есть в данных, но не описано в спецификации** — 11 путей из 114.
  Описание пишем сами и помечаем как своё.
- **Официальное описание расходится с данными.** `status.reasonName` описан
  как «причина закрытия организации», но все 200 компаний в статусе
  «действующая», а в поле лежит в том числе «признано несостоятельным
  (банкротом)». Верим данным, расхождение фиксируем.

## Requirements *(mandatory)*

### Functional Requirements

**Триггеры**

- **FR-001**: Система MUST выявлять противоречия между разными блоками отчёта
  и показывать их отдельным списком на карточке контрагента.
- **FR-002**: Каждый триггер MUST называть поля, из которых он сложился,
  и раздел отчёта, где пользователь может проверить значения.
- **FR-003**: Система MUST NOT дублировать триггером то, что источник уже даёт
  готовым негативным признаком: пятнадцать таких признаков уже показываются
  разделами.
- **FR-004**: Триггер MUST срабатывать не более чем у трети набора. Признак,
  срабатывающий чаще, описывает не компанию, а рынок, и в список не входит.
- **FR-005**: Отсутствие сработавших триггеров MUST выражаться явной
  формулировкой, а не пустым местом.
- **FR-006**: Набор триггеров MUST быть проверяемым: для каждого записано, у
  скольких компаний из 200 он срабатывает, и эта величина проверяется тестом.
- **FR-007**: Отвергнутые кандидаты в триггеры MUST быть записаны вместе
  с причиной отказа, чтобы их не проверяли заново.

**Учёт вопроса пользователя**

- **FR-008**: Система MUST принимать вопрос пользователя своими словами
  и менять по нему **порядок** пунктов.
- **FR-009**: Система MUST NOT скрывать сработавший триггер из-за того, что
  вопрос был о другом.
- **FR-010**: Если вопрос не разобран или отсутствует, порядок MUST оставаться
  тем же, что и без вопроса.

**Словарь полей**

- **FR-011**: Система MUST хранить для каждого поля данных его описание
  человеческими словами и происхождение описания — из официальной спецификации
  кейсодателя или наше.
- **FR-012**: Каждое поле MUST нести теги: раздел отчёта, к которому оно
  относится, и то, на какой вопрос оно отвечает.
- **FR-013**: Подписи источников на экране MUST браться из словаря, а не быть
  путями внутри данных.
- **FR-014**: Словарь MUST покрывать все поля, которые продукт использует,
  и заявлять покрытие числом.
- **FR-015**: Расхождения между официальной спецификацией и данными MUST быть
  зафиксированы в словаре, а не молча разрешены в пользу одной из сторон.

### Key Entities

- **Триггер** — противоречие между блоками отчёта. Несёт: название понятное
  пользователю, объяснение, поля-основания, раздел отчёта для проверки,
  значимость, замеренную частоту срабатывания на наборе.
- **Словарная статья поля** — путь внутри данных, описание словами,
  происхождение описания, теги (раздел, вопрос, к кому относится), заполненность
  на наборе.
- **Вопрос пользователя** — свободный текст, из которого выводится намерение;
  намерение задаёт порядок триггеров, но не состав.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На карточке контрагента с противоречиями пользователь видит их
  список, не открывая ни одного раздела.
- **SC-002**: Ни один триггер не срабатывает более чем у трети набора;
  проверяется на всех 200 компаниях.
- **SC-003**: Каждый показанный триггер сопровождается полями-основаниями
  и разделом для проверки — 100% пунктов, без исключений.
- **SC-004**: Два разных вопроса по одной компании дают разный порядок пунктов
  при неизменном их составе.
- **SC-005**: Ни одна подпись источника на экране не содержит путей внутри
  данных (квадратных скобок, точек пути, латинских имён полей).
- **SC-006**: Словарь покрывает описанием 100% полей, которые продукт
  показывает пользователю или отдаёт модели.
- **SC-007**: Для каждого триггера в наборе записана замеренная частота, и она
  сходится с фактической при прогоне на данных.

## Assumptions

- **Вопрос меняет порядок, а не состав.** Пользователь просил «учитывать query
  при отфильтровывании рисков». Скрывать сработавший признак потому, что вопрос
  был про другое, опасно: спросивший про выручку не должен пропустить
  банкротство. Поэтому вопрос поднимает относящееся к нему наверх, а не убирает
  остальное. Если это решение неверно, оно меняет FR-009 и SC-004.
- **Пороги триггеров — черновые.** Выбраны по одному прогону на 200 компаниях
  и обоснованы только частотой срабатывания. Каждый порог задаётся явно и
  проверяется тестом, чтобы его можно было пересмотреть, увидев замер.
- **Описания берутся из официальной спецификации кейсодателя**
  (`data/GetFullReportResponse.md`, 122 поля), а не сочиняются: 103 поля из 114,
  встречающихся в данных, там уже описаны.
- **RAG в объём не входит.** Словарь строится так, чтобы подбор контекста
  по тегам был возможен позже, но сам подбор не делается.
- **Мониторинг изменений во времени не входит.** В выгрузке один срез на дату,
  второго снапшота нет — триггер вида «положение ухудшилось» построить не на чем.
- Набор данных остаётся тем же: 200 компаний, один срез, без обновлений.
