# Implementation Plan: Триггеры из данных и словарь полей

**Branch**: `009-risk-triggers` | **Date**: 2026-09-05 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/009-risk-triggers/spec.md`

## Summary

Два слоя поверх существующего отчёта, оба — чистые функции в ядре.

**Триггеры** — противоречия между блоками отчёта, которых не видно ни в одном
поле по отдельности. Считаются детерминированно, без модели. Каждый называет
поля-основания и раздел для проверки. Показываются отдельным блоком на карточке
и уходят в промпт агента.

**Словарь полей** — описание и теги для каждого пути внутри данных. Собирается
из официальной спецификации кейсодателя один раз скриптом и коммитится, потому
что сама спецификация лежит вне репозитория. Даёт подписи источников словами
вместо путей JSON и готовит почву для будущего подбора контекста по тегам.

**Вопрос пользователя** меняет порядок триггеров по правилам, без вызова модели:
каждое намерение — это набор тегов, порядок задаётся их пересечением с тегами
триггера.

## Technical Context

**Language/Version**: Python 3.12 (ядро, API), TypeScript + React (интерфейс)

**Primary Dependencies**: без новых. Триггеры и словарь — стандартная библиотека;
отрисовка — уже установленный `@alfalab/core-components`

**Storage**: словарь полей — файл в репозитории, генерируется скриптом
из `data/GetFullReportResponse.md` и набора; в рантайме читается как данные

**Testing**: pytest. Частота срабатывания каждого триггера закрепляется тестом
на настоящем наборе (маркер `нужен_набор`), логика — на синтетических записях

**Target Platform**: тот же контейнер, что и сейчас

**Project Type**: web (ядро + API + фронт), структура уже сложилась

**Performance Goals**: триггеры считаются на каждый показ отчёта, поэтому
без обращений к сети и модели. Бюджет — единицы миллисекунд на компанию

**Constraints**: сервер 894 МБ. Словарь читается один раз на процесс, как набор.
Триггеры не копируют запись — работают по ссылке

**Scale/Scope**: 200 компаний, 114 путей в данных, 12 кандидатов в триггеры,
из них после отбора остаётся 10

## Constitution Check

| Принцип | Как соблюдается |
|---|---|
| **I. Спека первична** | спека и план написаны до кода; замеры сделаны до спеки и в неё вошли |
| **II. Ядро не знает протоколов** | `core/triggers.py` и `core/fields.py` — чистые функции от записи, без сети и моделей. Порядок по вопросу тоже в ядре: это правило, а не вызов |
| **III. Минимальная реализация** | намерение вопроса разбирается ключевыми словами, а не моделью: вызов на каждый вопрос стоил бы задержки и токенов ради упорядочивания |
| **IV. Требования кейсодателя** | триггер обращает внимание, а не выносит вердикт: формулировки «обратите внимание», без «не заключать договор». Свой скоринг не строится — триггер это наблюдение о противоречии, а не оценка |
| **IV. Отсутствие данных — ответ** | «отчётности нет» существует отдельным триггером, а не молчанием |
| **V. Отбор полей** | триггеры считаются по записи в ядре и в промпт уходят строками, а не сырьём |

**Structure Decision**: раскладка проекта уже сложилась (`src/core`, `src/api`,
`src/web`), новые модули встают в неё без изменений границ.

**Почему словарь генерируется и коммитится, а не читается в рантайме.**
`data/` — симлинк на каталог вне репозитория, в образ он не попадает, на сервере
его нет. Читать спецификацию при старте невозможно. Поэтому скрипт превращает её
в `src/core/fields.json` один раз, файл коммитится и едет внутри образа. Тем же
приёмом собран набор (`scripts/build_dataset.py`), только набор не коммитится —
в нём ФИО учредителей, а в словаре только имена полей и описания.
