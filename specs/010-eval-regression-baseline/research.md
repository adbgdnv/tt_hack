# Research: Живой eval-набор для агента проверки контрагентов

Спека не содержит нерешённых `[NEEDS CLARIFICATION]`. Ниже — решения по интеграции
уже готового пакета, которые не были очевидны из спеки и требовали проверки против
текущего состояния репозитория `alfa`.

## 1. Куда класть юнит-тесты пакета

**Decision**: Переносим `tests/test_eval_*.py` из исходного пакета прямо в
существующий `tests/` репозитория, без отдельного `testpaths`.

**Rationale**: `pyproject.toml` уже задаёт `testpaths = ["tests"]` и
`pythonpath = ["src", "."]` — файлы, которые лежат в `tests/`, подхватываются `pytest`
без правок конфигурации. Сами тесты пакета самодостаточны (используют только
`evals.*` через фейки/`SimpleNamespace`, не трогают `core`/`api` на уровне импорта
модуля) — переезд не меняет их поведение.

**Alternatives considered**: оставить тесты внутри `evals/tests/` рядом с пакетом —
отклонено, потребовало бы либо второй записи в `testpaths`, либо ручного запуска
`pytest evals/tests`, что ломает существующую привычку `pytest -q` находить всё в
одном месте.

## 2. Разница интерпретаторов Python на машине разработки

**Decision**: Новые таргеты `Makefile` (`eval-build`, `eval-regression`, `eval-risk`,
`eval-baseline`) вызывают `python3.13` явно, а не `python3`/`pytest` без версии.

**Rationale**: На машине разработки зависимости (`langchain`, `langgraph` и т.д.)
стоят в Python 3.13, а `python3`/`pytest` в `PATH` резолвятся в 3.14 без них — попытка
запустить живой прогон через голый `python3 -m evals.run` упадёt на
`ModuleNotFoundError` ещё до обращения к данным. Существующий таргет `test:` в
`Makefile` этой развилки не учитывает (известная отдельная проблема) — чинить его в
рамках этой фичи не входит в скоуп (принцип III конституции: смежная проблема — новая
фича), но **новые** таргеты не должны наследовать ту же ловушку.

**Alternatives considered**: полагаться на активный `venv`/`pip install -e ".[dev]"`
перед прогоном без явного указания интерпретатора — отклонено, потому что именно это
уже один раз привело к молчаливому попаданию в `pytest` из другого интерпретатора.

## 3. Что именно исключать из git

**Decision**: В `.gitignore` добавляются `evals/datasets/` и `evals/results/`
(с оговоркой `!evals/datasets/.gitkeep` / `!evals/results/.gitkeep`, чтобы сама
структура каталогов версионировалась, а сгенерированные файлы — нет).

**Rationale**: `evals/datasets/generated.jsonl` содержит реальные ИНН (это уже было
условием исходного пакета). Проверка показала, что `evals/results/*.json` тоже
чувствителен: `CaseResult`/`EvalTrace` включают полный текст ответов агента, в
которых естественным образом фигурируют названия компаний, суммы исков и прочие факты
из отчёта — то же обязательство «реальные ИНН/данные контрагентов не в git», что и
для датасета, распространяется и на результаты. Существующий `dataset/` и `data`
(симлинк на `../docs_alpha`) уже игнорируются тем же `.gitignore` — паттерн
продолжается, а не изобретается заново.

**Alternatives considered**: игнорировать только `evals/datasets/`, оставить
`evals/results/baseline.json` версionируемым как «эталон для сравнения» — отклонено:
эталон нужен команде локально и для демо, но сам факт коммита обезличивать не даёт
смысла — компании и суммы всё равно останутся в тексте ответов.

## 4. Совместимость сигнатур с текущим кодом продукта

**Decision**: Перенос без адаптации сигнатур — интерфейсы уже совпадают.

**Rationale**: Прямая сверка против `src/`:

| Пакет ожидает | Реальная сигнатура в `alfa` |
|---|---|
| `core.repo.all() -> list[dict]` | `src/core/repo.py:86` — совпадает |
| `core.repo.by_inn(inn) -> dict \| None` | `src/core/repo.py:57` — совпадает |
| `core.report.build(record) -> Report` | `src/core/report.py:296` — совпадает |
| `core.charts.build_charts(record) -> tuple[ChartSpec, ...]` | `src/core/charts.py:263` — совпадает |
| `api.agent.tools.build(record, inn) -> list` | `src/api/agent/tools.py:88` — совпадает |
| `api.agent.loop.Session`, `loop.run(state, report, record, question, tools) -> Answer` | `src/api/agent/loop.py:45,158` — совпадает, включая поля `Answer.text/charts/sources` |

**Alternatives considered**: не было — расхождений не найдено, адаптационный слой не
нужен.

## 5. Импорт `api.agent` из инструмента вне `src/core`

**Decision**: не считается нарушением границы ядра.

**Rationale**: Принцип II конституции ограничивает то, что импортирует `src/core`
(ядро не должно знать о HTTP/MCP-обвязке), а не то, кто импортирует `core`/`api`
снаружи. Прецедент уже есть: `tests/test_agent.py`, `tests/test_tools.py`,
`tests/test_search.py` импортируют `api.agent.*` напрямую. `evals/` — инструмент
разработки того же рода, что `tests/`, и следует тому же прецеденту.

## 6. Готовность входных данных

**Decision**: дополнительная подготовка данных перед сборкой eval-датасета не
требуется.

**Rationale**: `dataset/counterparties.json` уже существует в рабочей копии (собран
`scripts/build_dataset.py`, ~200 контрагентов, 3.4 МБ) и уже используется продуктом
через `DATASET_PATH`/`core.repo.load`. Живой прогон и сборка кейсов могут запускаться
сразу, без дополнительного шага генерации.

## 7. Лимиты провайдера при живом прогоне (обнаружено на T020, не было в исходном плане)

**Decision**: `evals/runners/current_agent.py` оборачивает вызов агента ретраем на
`openai.RateLimitError` — до 4 попыток, ожидание берётся из текста ошибки
(`"try again in <N>s"` или `"try again in <M>m<N>s"`), но только если оно не длиннее
60 секунд; более долгое ожидание не ретраится — кейс сразу становится `infra_error`.

**Rationale**: первый живой прогон без ретрая дал 27 `infra_errors` из 30 — все по
лимиту **TPM** (8000 токенов/мин у Groq на free-тире), потому что раннер вызывает
агента 30 раз подряд без паузы. С ретраем их стало 4. Разбор оставшихся четырёх
показал второй, более редкий лимит — **TPD** (200 000 токенов/сутки на всю
организацию, общий для всего трафика, не только eval): провайдер называет то же
`"try again in ..."`, но ждать приходится 15–20 минут. Ретраить это внутри одного
прогона бессмысленно — 30-кейсовый прогон не должен зависать на четверть часа ради
одного кейса, поэтому потолок ожидания (`_MAX_RETRY_WAIT_SECONDS = 60`) отделяет
«подождать и повторить» (TPM) от «зафиксировать как инфраструктурную ошибку сразу»
(TPD). Оба сценария подтверждены живыми вызовами: ретрай на TPM-паузы работает
(снижение 27→4), а быстрый отказ на TPD-паузы проверен отдельным `--limit 1`-прогоном
(вернулся мгновенно, а не через 13+ минут).

**Alternatives considered**: не добавлять ретрай вовсе и просто уменьшить размер
живого прогона — отклонено: без ретрая FR-006/SC-002/SC-003 не выполняются на
единственном настроенном провайдере, а это условие работоспособности самой User
Story 1, а не отдельный запрет из спеки. Ретраить и TPD-паузы тоже (просто с более
длинным ожиданием) — отклонено: заблокировало бы весь прогон на десятки минут ради
одного кейса без гарантии, что квота вообще успеет освободиться до истечения
разумного времени ожидания разработчика.
