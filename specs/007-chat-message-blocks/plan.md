# Implementation Plan: Ответ в чате читается как ответ

**Branch**: `007-chat-message-blocks` | **Date**: 2026-09-04 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/007-chat-message-blocks/spec.md`

## Summary

Две поломки в выводе ответа, обе видны на первом же ответе с инструментом:
разметка показывается сырой, а один вызов инструмента разорван на три места —
отметка сверху, график в середине, ссылки в самом низу.

Чинится **только интерфейс**. Сервер уже отдаёт события в порядке возникновения
и порядок гарантирует контрактом; интерфейс раскладывает их по трём отдельным
спискам и порядок теряет.

Опора — рабочая реализация в `zorox-editor`, разобранная по коду. Оттуда берём
модель упорядоченных блоков и три уровня защиты от тормозов при печати. Три их
недоработки повторять не будем: ошибка инструмента там выглядит как успех,
оборванный поток оставляет вызов вечно крутящимся, внешние ссылки открываются
без защиты вкладки.

## Technical Context

**Language/Version**: TypeScript, React 18.3.1

**Primary Dependencies**: `react-markdown@10` + `remark-gfm@4` (проверено:
`peerDependencies` требует `react >= 18`); `@alfalab/core-components-collapse`
уже в зависимостях

**Storage**: состояние диалога в памяти вкладки, как и было

**Testing**: проверка глазами по `quickstart.md`; `tsc --noEmit` для типов.
Серверные тесты должны остаться зелёными без правок — это и есть доказательство,
что фича только про интерфейс

**Target Platform**: браузер, панель чата рядом с дашбордом

**Project Type**: веб-интерфейс поверх готового потокового протокола

**Performance Goals**: ответ на 500 слов печатается без видимых рывков;
готовые части не разбираются заново

**Constraints**: собранный файл уже около 830 КБ — прирост от разбора разметки
надо измерить, а не оценить

**Scale/Scope**: один компонент чата, один новый компонент блока вызова,
две новые зависимости

**Structure Decision**: разбор разметки и блок вызова выносятся отдельными
компонентами, а не остаются внутри `ChatPanel`. Причина не в аккуратности:
**мемоизация работает только на отдельном компоненте**. Разбор, оставленный
внутри панели, будет пересобираться на каждое слово вместе со всей лентой —
ровно та беда, из-за которой в референсе появился отдельный мемоизированный
компонент разметки.

## Порядок работ

Три среза, каждый проверяем сам по себе.

**Срез 1 — разметка** (US1). Библиотека, компонент разбора, переопределённая
ссылка, прокрутка таблицы. Проверяется на любом ответе, инструменты не нужны.

**Срез 2 — блоки** (US2). Накопление блоков вместо трёх списков, компонент
вызова со сворачиванием, результат внутри вызова, четыре состояния. Здесь же
перевод незавершённых вызовов в «прервано» по окончании потока.

**Срез 3 — плавность** (US3). Мемоизация разбора, склейка потока раз в кадр,
курсор набора вне разбора. Идёт последним намеренно: пока блоки не устоялись,
мемоизировать нечего, а преждевременная оптимизация помешает отладке.

## Complexity Tracking

| Усложнение | Зачем | Почему не проще |
|---|---|---|
| `react-markdown` + `remark-gfm` | разобрать произвольную разметку ответа | свой разбор дал бы ошибки именно там, где пользователь должен верить тексту; `marked` со вставкой готовой разметки потребовал бы санитизации, а дыра в ней превращает ответ внешней модели в исполняемый код |
| Отдельные компоненты разметки и вызова | мемоизация работает только на компоненте | оставить внутри панели — значит разбирать всю ленту на каждое слово |
| Четвёртое состояние вызова «прервано» | поток рвётся между началом и концом вызова | без него вызов крутится вечно и уходит в историю в таком виде — это ровно то, что происходит в референсе |

Прирост веса собранного файла измеряется на реальной сборке и записывается
в задачу полировки. Если он окажется значимым — разбор разметки грузится
отдельным куском: он нужен только на экране с чатом.

## Что осталось за рамками

- **Протокол потока** — не меняется. Если по ходу выяснится, что порядок теряется
  и на сервере, это отдельная правка.
- **Починка недописанной разметки на лету** — не делаем: значило бы угадывать
  намерение модели.
- **Перенос старых сообщений** в новый вид — память живёт в рамках сессии.
