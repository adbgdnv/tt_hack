# Tasks: Дашборд отчёта и диалог о контрагенте

**Input**: Design documents from `/specs/003-report-dashboard-chat/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/](./contracts/)

**Tests**: включены. Конституция требует проверяемости каждой задачи и зелёного CI,
а критерий «не выдумывает» проверяется только прогоном: действующий промпт уже
содержал правило про рекомендательный тон и всё равно выдал категоричное
«Не стоит работать с компанией».

**Organization**: задачи сгруппированы по историям. Сборка представления отчёта вынесена
в фундамент, потому что ею пользуются обе истории первого приоритета: интерфейс её
показывает, диалог по ней отвечает.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: можно делать параллельно — разные файлы, нет незакрытых зависимостей
- **[Story]**: к какой истории относится задача (US1, US2, US3)
- В описании указан точный путь к файлу

## Path Conventions

`src/core/` — доменная логика, `src/api/` — HTTP и оркестрация диалога,
`src/web/` — интерфейс, `tests/` в корне. Раскладка из [plan.md](./plan.md).

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: без зависимостей
- **Foundational (Phase 2)**: после Setup. **Блокирует US1 и US2**
- **US1 (Phase 3)**: после Foundational
- **US2 (Phase 4)**: после Foundational. От US1 не зависит: диалогу нужно представление отчёта, а не его отрисовка
- **US3 (Phase 5)**: после Setup. От фундамента не зависит вовсе — трогает только честность интерфейса
- **Polish (Phase 6)**: после поставленных историй

### User Story Dependencies

- **US1 (P1)**: самостоятельна. Даёт читаемый отчёт без диалога
- **US2 (P1)**: самостоятельна. Единственное пересечение с US1 — общее представление отчёта, готовое в фундаменте
- **US3 (P2)**: полностью независима, может идти параллельно с чем угодно после Setup

### Within Each User Story

- Ядро перед приложением, приложение перед интерфейсом
- Тесты пишутся до реализации и должны падать до неё
- История закрывается целиком до перехода к следующей

### Parallel Opportunities

- T002 параллельна T001
- В фундаменте: T004 параллельна T005–T008, это разные файлы
- В US1: T012 параллельна интерфейсным T013–T017; T019 параллельна T018
- В US2: T024 параллельна T025–T027
- **US3 целиком параллельна US1 и US2** — она не касается ни ядра, ни диалога
- В Polish: T036 и T037 параллельны

## Implementation Strategy

### MVP — Setup + Foundational + US1

Отчёт читается, разделы упорядочены, формулировки русские. Показывать можно уже здесь:
это первый экран продукта, и без него диалог не о чем вести.

### Инкрементальная поставка

1. Setup + Foundational → представление отчёта собирается
2. US1 → первый экран отвечает на «что не так» → **MVP, можно показывать**
3. US2 → диалог отвечает по данным → показывать
4. US3 → интерфейс перестаёт обманывать → показывать
5. Polish → документация и полный прогон

### Порядок при нехватке времени

US1 и US2 обе первого приоритета, но если резать — **US2 дороже**: критерий приёмки
кейса про «не выдумывает» проверяется именно диалогом, а отчёт без диалога остаётся
осмысленным продуктом. US3 дешевле обеих и даёт заметный эффект на защите: нерабочая
кнопка «PDF» портит впечатление сильнее, чем её отсутствие.
