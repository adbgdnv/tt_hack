# Implementation Plan: Сильная модель, данные по тегам и проверка утверждений

**Branch**: `010-agent-upgrade` | **Date**: 2026-09-05 | **Spec**: [spec.md](spec.md)

## Summary

Четыре правки, три из них небольшие.

**Провайдер** переезжает на OpenRouter, рассуждение включается обратно, Groq
остаётся запасным путём. Правится настройка и один модуль клиента.

**Инструмент `look_up`** даёт агенту данные по одной из восьми тем — то, чего
нет в собранном отчёте. Темы выводятся из тегов словаря полей, у судов
и взысканий отдаётся сводка вместо перечня.

**Проверка утверждений** лестницей: числа из ответа сверяются с отчётом кодом,
модель зовётся только когда не сошлось.

**Диалог** раскрывается по фокусу в поле ввода.

## Technical Context

**Language/Version**: Python 3.12 (ядро, API), TypeScript + React (интерфейс)

**Primary Dependencies**: без новых. Клиент уже OpenAI-совместимый, инструменты
уже собираются в `api/agent/tools.py`, словарь тегов уже есть

**Storage**: нет. Темы — производная от `src/core/fields.json`

**Testing**: pytest. Сводки по темам и проверка чисел — на настоящем наборе;
переключение провайдера — подменой окружения

**Target Platform**: тот же контейнер

**Project Type**: web, структура сложилась

**Performance Goals**: ответ не дольше, чем сейчас ощущается диалог. Замерено:
одиночный вызов на OpenRouter 4,7 с у `deepseek v4 flash`, 7,1 с у `glm 5.3
flash`. Полный ответ с инструментами не замерен — проверить первым делом

**Constraints**: тема отдаётся не целиком, если она большая; потолок на ответ
инструмента такой же жёсткий, как у чтения страниц. Проверка чисел не должна
добавлять вызовов, когда всё сошлось

**Scale/Scope**: 200 компаний, 8 тем, 114 полей словаря

## Constitution Check

| Принцип | Как соблюдается |
|---|---|
| **I. Спека первична** | спека и замеры написаны до кода; отменённое записано в архитектуру |
| **II. Ядро не знает протоколов** | темы и сводки считаются в `core`, инструмент-обёртка живёт в `api/agent`; проверка чисел — тоже ядро, это чистая функция |
| **III. Минимальная реализация** | перечень из восьми тем вместо векторного хранилища; сверка числами вместо второго агента |
| **IV. Требования кейсодателя** | «модель видит ровно то, что видит пользователь» держится: взятое по теме показывается блоком вызова. Агент по-прежнему обращает внимание, а не выносит вердикт |
| **IV. Отсутствие данных — ответ** | пустая тема отвечает «таких данных нет», а не молчит |
| **V. Отбор полей** | остаётся: отчёт в промпте, темы по запросу. Снятие лимита провайдера не повод класть запись целиком — причина не в лимите, а в проверяемости |

Отклонений нет.

**Structure Decision**: раскладка не меняется. Темы и проверка — чистые функции
над записью и отчётом, поэтому в ядре; инструмент — тонкая обёртка в агенте.

**Почему проверка в ядре, а не в агенте.** Она не знает ни про модель, ни про
протокол: на входе текст ответа и отчёт, на выходе список утверждений с отметкой.
Это делает её проверяемой без сети и переиспользуемой из MCP.

**Почему темы выводятся из словаря, а не пишутся заново.** Теги уже проставлены
у всех 114 полей в `src/core/fields.json`. Второй список тем разошёлся бы
с первым в первый же день.
