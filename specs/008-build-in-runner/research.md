# Phase 0 — исследование

## 1. Что именно сломалось и почему

Замерено сегодня, во время выкатки:

| | |
|---|---|
| Память сервера | **894 МБ** всего |
| Нагрузка во время сборки фронта | **27** |
| SSH | не доходил до приветствия |
| Сайт | не открывался |
| После отмены выкатки | контейнер `cc-web` в состоянии `Created`, сайт лежал |

Сборка веб-интерфейса — установка зависимостей и упаковка — на 894 МБ не влезает.
Свап на 2 ГБ, добавленный после, меняет «упало» на «медленно», но не убирает
причину.

Раннер GitHub: 4 ядра, 16 ГБ, бесплатно для публичного репозитория. Разница
в порядок величины.

## 2. Где хранить образы

**Решение**: GitHub Container Registry (`ghcr.io`).

Он идёт вместе с репозиторием: заводить и обслуживать свой реестр, как в
`zorox-editor` (`registry.zorox.io` внутри кластера), ради двух образов
и одного сервера незачем.

**Отвергнуто**: Docker Hub — отдельная учётка и лимиты на скачивание.
**Отвергнуто**: свой реестр на том же сервере — он и так задыхается.
**Отвергнуто**: собирать в раннере и класть образ артефактом, а на сервере
`docker load` — артефакты живут ограниченно, весят как образ целиком и
не дают откатиться на произвольную версию.

## 3. Как сервер получит доступ на чтение

**Решение**: одноразовый вход по временному токену задания, без долгоживущего
ключа на сервере.

У задания выкатки есть свой токен с правом чтения пакетов, живущий ровно столько,
сколько идёт задание. Он передаётся на сервер через stdin, там выполняется вход
в реестр, образы забираются, вход снимается. На сервере не остаётся ничего,
что можно украсть позже.

**Отвергнуто**: постоянный токен доступа в секретах и на сервере. Работает,
но кладёт на машину долгоживущий ключ к реестру — при том что альтернатива
не сложнее.

Осечка, которую надо иметь в виду: у задания по умолчанию нет права читать
пакеты — его надо запросить явно, иначе вход пройдёт, а скачивание упрётся
в отказ.

## 4. Форма конвейера

**Решение**: два задания в одном описании — `build` и `deploy`, второе
объявляет зависимость от первого.

Сейчас выкатка живёт отдельным описанием, которое слушает завершение проверок.
Это работает, но растягивает цепочку на три запуска и мешает объявить прямую
зависимость «выкатывать только собранное».

В `zorox-editor` это ровно один конвейер с этапами `lint → test → build → deploy`,
и `deploy` объявляет `needs: build:*`. Берём ту же форму: проверки → сборка →
выкатка, всё в одном месте.

**Что при этом теряется**: сегодняшний обход через `workflow_dispatch` для ручного
запуска выкатки без проверок. Оставляем его отдельным входом.

## 5. Кэш слоёв

**Решение**: кэш сборки, который хранит сам поставщик, плюс опора на предыдущий
образ.

В референсе перед сборкой тянется образ с меткой «последний» и передаётся
как основа для кэша. На GitHub есть более прямой путь — кэш сборки, живущий
у поставщика и не требующий предварительного скачивания образа.

Берём оба: кэш поставщика как основной, метка «последний» как запасной вариант,
если кэш пуст.

Важное из референса, стоившее им отдельного разбора: **кэшировать надо загрузки
пакетов, а не установленное дерево**. Они клали в кэш `node_modules` на 752 МБ,
которые установка первым же действием удаляет, — кэш замедлял, а не ускорял.
У нас это внутри слоя образа, но ошибку стоит помнить, если дойдёт до отдельного
кэша.

## 6. Что придётся поменять в описании контейнеров

Сейчас у сервиса `web` задан явный тег `cc-web:latest`, у `api` тега нет вовсе —
имя выводится из каталога проекта. Оба собираются из исходников прямо на сервере.

**Решение**: обоим сервисам задать имя образа в реестре с меткой из переменной;
раздел сборки оставить — он нужен для локального запуска.

Так один и тот же файл продолжает работать в двух режимах: локально собирает,
на сервере забирает готовое.

**Подводный камень**: при наличии раздела сборки команда подъёма может решить,
что образ надо собрать. На сервере подъём должен явно запрещать сборку — иначе
всё вернётся к тому, с чего начали, и обнаружится это в самый неподходящий момент.

## 7. Адрес API при сборке фронта

Фронту адрес API нужен **во время сборки** — он вшивается в собранный файл.
Сейчас он передаётся аргументом сборки в описании контейнеров.

Значение относительное (`/api`), не адрес сервера, поэтому оно одинаково локально
и на сервере, и передавать его секретом не нужно. При переносе сборки в раннер
аргумент надо передать там же — иначе фронт соберётся без адреса и будет ходить
в никуда, причём молча.

## 8. Что нельзя потерять при переносе

В нынешних скриптах выкатки накоплено несколько вещей, каждая появилась после
поломки:

| Что | Зачем появилось |
|---|---|
| Бэкенд выкатывается **до** фронта | обратный порядок ронял страницу в белый экран |
| Откат на предыдущий образ | не поднявшийся контейнер не должен оставлять сайт лежащим |
| Проверка `/` и `/api/health` после подъёма | контейнер, отдающий страницу без живого API, снаружи выглядит рабочим |
| Проверка здоровья по IPv4, не по имени | в образе имя резолвится только в IPv6, а сервер слушает IPv4 |
| Долгое ожидание в SSH | ставилось из-за молчаливой установки пакетов на сервере |

Первые четыре переносим. Пятая после переноса **становится не нужна** — на сервере
больше не будет долгих молчаливых операций, но убирать её в этой же правке
не станем: одна правка — одна причина.

## 9. Сколько версий хранить

Метка на каждый коммит означает рост хранилища. У поставщика есть готовое
средство удаления старых версий по расписанию.

**Решение**: хранить последние несколько версий, остальные удалять. Точное число —
вопрос плана, но оно должно быть больше единицы: смысл всей затеи в том, чтобы
было куда откатиться.
