# Implementation Plan: Сборка уезжает с боевого сервера

**Branch**: `008-build-in-runner` | **Date**: 2026-09-04 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/008-build-in-runner/spec.md`

## Summary

Оба образа собираются на боевом сервере с 894 МБ памяти. Сегодня это положило
сервис: нагрузка 27, SSH без ответа, страница не открывается; отмена выкатки
оставила контейнер «созданным, но не запущенным».

Переносим сборку в раннер (4 ядра, 16 ГБ, бесплатно для публичного репозитория),
образы кладём в реестр GitHub под меткой коммита, а сервер при выкатке только
забирает готовое и подменяет контейнеры.

Форма взята из `.gitlab-ci.yml` в `zorox-editor`: отдельный этап сборки, две метки
на образ, опора на предыдущий образ, зависимость выкатки от сборки, проверка после.

## Technical Context

**Language/Version**: GitHub Actions (YAML), Bash — скрипты выкатки на сервере;
Docker Compose

**Primary Dependencies**: `docker/build-push-action` и `docker/login-action`
для сборки и публикации; `ghcr.io` как реестр — идёт вместе с репозиторием

**Storage**: реестр образов GitHub; набор данных на сервере остаётся томом
и в образы не попадает

**Testing**: конвейер проверяется своим прогоном; серверные тесты и типы
не затрагиваются

**Target Platform**: раннер `ubuntu-latest` для сборки; один сервер Timeweb
для выкатки

**Project Type**: инфраструктура поставки, продуктовый код не меняется

**Performance Goals**: во время выкатки нагрузка сервера остаётся рабочей,
страница открывается за обычное время

**Constraints**: репозиторий публичный — минуты раннера бесплатны; сервер
894 МБ, и это не лечится, а обходится

**Scale/Scope**: два образа, один сервер, два задания в одном конвейере

## Порядок работ

**Срез 1 — сборка появляется, выкатка не меняется.** Задание `build` собирает
и публикует образы; выкатка продолжает собирать на сервере. Проверяется тем,
что в реестре появились образы с меткой коммита. Ничего не ломается: старый путь
цел.

**Срез 2 — выкатка переключается на готовое.** Скрипты на сервере забирают образ
вместо сборки; compose ссылается на реестр. Здесь и снимается нагрузка.

**Срез 3 — откат и уборка.** Ручной откат по метке, ограничение числа хранимых
версий, документация.

Порядок такой, потому что срез 1 обратим целиком, а срез 2 — точка, после которой
сервер уже не умеет собирать сам.

## Риски

| Риск | Что делаем |
|---|---|
| **Первый прогон нового конвейера — на живом сервере**, другого нет | срез 1 ничего не меняет в выкатке; срез 2 включается отдельным коммитом, когда сборка уже проверена |
| Подъём на сервере решит собрать образ вместо того, чтобы взять готовый | запрещаем сборку явным флагом; это же проверяется в quickstart |
| У задания нет права читать пакеты — вход пройдёт, скачивание упадёт | право запрашивается явно; проверяется на первом же прогоне |
| Фронт соберётся без адреса API и будет молча ходить в никуда | аргумент сборки переносится в раннер вместе со сборкой, проверяется по собранному файлу |
| Правка конвейера ломает выкатку прямо перед финалом | старые скрипты не удаляются до успешного прогона нового пути |

## Что осталось за рамками

- **Перенос на кластер** — сервер один, и этого достаточно.
- **Автоматический откат по метрикам** — откат остаётся действием человека.
- **Изменение содержимого образов** — собирается ровно то же, что и раньше.
- **Уборка долгого ожидания в SSH**, которое ставилось из-за молчаливой сборки
  на сервере. После переноса оно не нужно, но убирать его в этой же правке
  не станем: одна правка — одна причина.
