# Phase 0 — исследование

Всё ниже проверено вживую на Groq `openai/gpt-oss-20b` и на живом ключе Tavily,
а не взято из документации. Даты замеров — 4 сентября 2026.

## 1. Инструмент, возвращающий только ключ, заставляет модель выдумывать

**Решение**: результат инструмента показа графика содержит и указание интерфейсу,
какой график рисовать, и **сами числа этого графика текстом для модели**.

**Как выяснилось.** Первая проба сделала ровно то, что было записано в спеке:
инструмент вернул `"показан"`. Модель вызвала его и дописала ответ **выдуманной
таблицей**:

```
| Год  | Дел | Сумма |
| 2019 |   3 |  0,45 |
| 2020 |   5 |  0,78 |
...
> Примечание: данные основаны на публичных реестрах арбитражных дел
```

Ни одного из этих чисел в отчёте нет. Компания зарегистрирована 9 лет назад,
но арбитраж в данных начинается с 2023 года; строки за 2019–2022 придуманы
целиком, вместе со ссылкой на несуществующий источник.

**Почему так вышло.** Голое подтверждение не даёт модели ничего, о чём говорить,
а пользователь спросил «объясни график». Пустота заполняется правдоподобным.

**Проверка исправления.** С числами в результате инструмента модель выдала
таблицу, совпадающую с отчётом: 2023 — 5 832 755 как истец и 0 как ответчик,
2024 — 382 176 765 и 2 589 790 444.

**Что это значит для реализации.** Разделение остаётся, но проходит по другой
границе, чем записано в исходном описании: интерфейсу — ключ (чтобы рисовал
своим кодом и не разошёлся с дашбордом), модели — числа (чтобы говорила о них,
а не о воображаемых). Источник у обоих один — построители `core/charts.py`.

**Отвергнуто**: возвращать модели готовый текст-описание графика. Тогда описание
пишет код, а не модель, и на вопрос «а что тут странного» ответить нечем.

## 2. Модель выбирает график по английскому ключу и промахивается

**Решение**: в описании инструмента каждый ключ сопровождается тем же русским
названием, которое видно на дашборде.

**Как выяснилось.** Дважды на просьбу «покажи суммы исков по годам» модель
выбрала `plaintiff_defendant` («В какой роли судится») вместо `arbitration_years`,
который так и называется — «Суммы исков по годам». Ключи латиницей, вопрос
по-русски, совпадение ищется вслепую.

В одной из проб модель исправилась сама, вызвав инструмент второй раз с верным
ключом. Это стоило лишнего вызова модели — при квоте 8 000 токенов в минуту такая
самокоррекция обходится дороже, чем правильное описание.

## 3. Прямой путь к агенту в LangChain 1.x

**Решение**: `langchain.agents.create_agent`, состояние сверх сообщений —
через `context_schema`.

`langgraph.prebuilt.create_react_agent` при вызове печатает предупреждение:
переехал в `langchain.agents.create_agent`, объявлен устаревшим в LangGraph 1.0
и будет удалён в 2.0. Устанавливать зависимость, помеченную к удалению, незачем.

У `create_agent` есть `context_schema` — это ровно то, что нужно: запись о компании
кладётся в контекст выполнения, инструмент достаёт её через `get_runtime`,
и в промпт запись не попадает. Проверено: инструмент прочитал запись из контекста
и построил график.

**Отвергнуто**: замыкание инструментов на запись при каждом запросе. Работает,
но пересобирает граф на каждое сообщение и размазывает состояние по замыканиям
вместо явного объявления.

## 4. События потока

**Решение**: `stream_mode="messages"`, разбор по типу куска.

Замерено на реальном прогоне: 572 куска `AIMessageChunk` и 1 `ToolMessage`
на один ответ с вызовом инструмента. Куски текста и вызовы инструментов приходят
одним типом — вызов опознаётся по непустому `tool_call_chunks`, где имя инструмента
приходит в первом куске, а аргументы дособираются в следующих. Итог инструмента —
отдельный тип `ToolMessage`. Сопутствующие метаданные несут `langgraph_node`,
по которому видно, из какого узла графа пришёл кусок.

Этого достаточно для всех событий, нужных интерфейсу: текст, начало вызова,
итог вызова, ошибка, конец.

## 5. Поиск: берём одну возможность из пяти

**Решение**: подключаемся к MCP-серверу Tavily, но модели описываем **только поиск**,
и описываем его своей узкой схемой.

**Замерено на живом ключе.** Сервер `mcp.tavily.com` отдаёт пять инструментов:

| Инструмент | Схема в токенах |
|---|---:|
| `tavily_search` | 890 |
| `tavily_crawl` | 594 |
| `tavily_map` | 398 |
| `tavily_extract` | 267 |
| `tavily_research` | 232 |
| **все пять** | **2383** |

Схемы инструментов уходят в модель **на каждом вызове**. Все пять — это треть
минутной квоты, потраченная на перечисление возможностей, которыми продукт
не пользуется. Даже один `tavily_search` со всеми необязательными параметрами
стоит 890 токенов.

Поэтому наружу модели идёт собственный инструмент с единственным параметром
`query` (около 60 токенов схемы), а под ним вызывается инструмент их MCP
с зафиксированными нами разумными значениями остальных параметров.

**Проверка полезности.** Запрос «ООО МАКСМАРКЕТ ИНН 5032257375 банкротство» вернул
Контур.Фокус и Rusprofile, оба подтверждают процедуру банкротства — то есть
источники ровно из списка «Материалы и данные» в описании кейса. Один ответ
поиска без урезания — 573 токена.

**Отвергнуто**: библиотека Tavily вместо их MCP. По просьбе пользователя и потому,
что MCP-клиент — это ещё и прямой ответ организаторам, которые «видят решение
как MCP-тул»: продукт оказывается по обе стороны протокола.

## 6. Бюджет токенов — главное ограничение реализации

Замерено на живом провайдере: текущий вопрос без инструментов стоит **1735 токенов
входа**. С инструментами:

| Составляющая | Токенов |
|---|---:|
| Промпт с личностью и границами | 266 |
| Собранный отчёт | 1469 |
| Схемы двух наших инструментов | ~180 |
| **Вход первого вызова** | **~1915** |
| Резерв ответа | 700 |
| Результат инструмента (поиск, урезанный) | ~400 |
| **Вход второго вызова** | **~2315** |
| **Итого на один вопрос с инструментом** | **~5330** |

При лимите 8 000 токенов в минуту это **один такой вопрос в минуту**. Убрать отчёт
из контекста нельзя — на нём стоит проверяемость ответа. Решается платным ключом,
кодом не решается; зафиксировано в спеке как внешний риск.

## 7. Бюджет ответа должен быть щедрым

`gpt-oss` тратит на рассуждение отдельные токены из того же лимита. При
`max_tokens=350` в одной из проб рассуждение съело весь бюджет и ответ после
вызова инструмента пришёл **пустым**. Это уже известное свойство модели, записанное
в коде клиента, но с инструментами оно опаснее: пустой ответ приходит уже после
того, как пользователь увидел вызов инструмента, и выглядит как поломка.

Держим не меньше 700 и проверяем пустой ответ как ошибку — цикл диалога это уже
делает.

## 8. Транспорт

**Решение**: server-sent events поверх обычного POST.

Двусторонний канал не нужен: клиент отправляет вопрос один раз и дальше только
слушает. Веб-сокет добавил бы протокол, настройку прокси и переподключения — ради
ничего.

`EventSource` в браузере не умеет POST, поэтому поток читается через `fetch`
и `ReadableStream`. Это не обходной путь, а обычная практика для SSE с телом
запроса.

**Подводный камень**: nginx по умолчанию буферизует ответ и отдаёт его целиком.
Снаружи это выглядит как полностью исправный сервер без стриминга. В блоке
`/api/` нужен `proxy_buffering off`.
