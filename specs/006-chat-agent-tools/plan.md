# Implementation Plan: Чат становится агентом с инструментами

**Branch**: `006-chat-agent-tools` | **Date**: 2026-09-04 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/006-chat-agent-tools/spec.md`

## Summary

Диалог перестаёт быть одним вызовом модели и становится агентом с двумя
инструментами. Ответ идёт потоком, график рисуется по просьбе, при нехватке
данных агент смотрит наружу через MCP-сервер поставщика поиска, и всё это время
пользователь видит, чем агент занят.

Три решения определяют реализацию, и все три получены замерами, а не рассуждением
(подробности — [research.md](research.md)):

1. **Запись о компании в промпт не идёт** — 31 000 токенов на типовой компании
   при квоте 8 000 в минуту. Она живёт в контексте выполнения агента, инструменты
   читают её оттуда.
2. **Инструмент графика возвращает числа модели и ключ интерфейсу.** С голым
   подтверждением «показан» модель дописала ответ выдуманной таблицей за
   2019–2022 годы. Это не гипотеза, это случилось на первой пробе.
3. **Из пяти инструментов MCP-сервера поставщика описываем модели один.** Все пять
   стоят 2383 токена на каждом вызове — треть минутной квоты на перечисление
   неиспользуемого.

## Technical Context

**Language/Version**: Python 3.12 (сервер), TypeScript + React (интерфейс)

**Primary Dependencies**: FastAPI, `langchain` 1.4 (`create_agent`), `langgraph` 1.2,
`langchain-openai`, `langchain-mcp-adapters` — к MCP поставщика поиска

**Storage**: подготовленный набор из 200 контрагентов, файл; состояние диалога —
в памяти процесса

**Testing**: pytest, без обращений к сети

**Target Platform**: Linux-сервер за nginx, докер-контейнер

**Project Type**: веб-сервис с отдельным фронтендом

**Performance Goals**: первый фрагмент ответа виден не позже 2 с; о начале работы
инструмента известно не позже 1 с

**Constraints**: 8 000 токенов в минуту у провайдера модели — определяющее
ограничение. Один вопрос с инструментом стоит ~5 300 токенов, то есть примерно
один такой вопрос в минуту. Отчёт из контекста убрать нельзя: на нём стоит
проверяемость.

**Scale/Scope**: 200 компаний, 5 видов графиков, 2 инструмента, 7 типов событий
потока

## Constitution Check

*GATE: проверено до Phase 0 и повторно после Phase 1.*

| Принцип | Как соблюдается |
|---|---|
| **I. Спека первична** | спека, исследование, контракты и проверка написаны до кода |
| **II. Ядро не знает про протоколы** | инструменты и клиент MCP живут в `src/api/agent/`, не в `src/core`. Конституция называет MCP явно — клиент поиска в ядро не попадает. Проверка держится: удалить `src/api` — `src/mcp_server` работает |
| **III. Минимальная реализация** | два инструмента, а не пять; один инструмент показа графика, а не пять по числу видов; SSE, а не веб-сокет |
| **IV. Требования кейсодателя** | светофоры не пересчитываются; «Графики обязательны» — US2; «Прогресс обработки показывать надо» — US1 и US3; память в рамках сессии не меняется |
| **V. Отбор полей** | усилен: запись не идёт в промпт вовсе, идёт только собранный отчёт |

**Повторная проверка после Phase 1**: нарушений не добавилось. Единственное
усложнение — три новые зависимости, обосновано ниже.

**Structure Decision**: агент целиком живёт в `src/api/agent/` — там же, где
он живёт сейчас. В ядро не переезжает ничего: инструменты знают про протокол
вызова модели, а клиент поиска — про MCP, и то и другое конституция из ядра
исключает. `core/charts.py` при этом остаётся единственным источником чисел
для графиков, и чат обращается к нему через инструмент, а не пересчитывает.

## Порядок работ

Три среза, каждый проверяем сам по себе.

**Срез 1 — поток без инструментов** (US1). Ручка `/chat/stream`, события `token`,
`error`, `done`, чтение потока во фронте, `proxy_buffering off` в nginx.
Проверяется без единого инструмента: ответ на обычный вопрос идёт словами.

**Срез 2 — график и видимость работы** (US2 + US3). Агент на `create_agent`,
контекст с записью, инструмент `show_chart`, события `tool_start`, `tool_end`,
`chart`, отрисовка в ленте. US3 без US2 нечего показывать, поэтому идут вместе.

**Срез 3 — взгляд наружу** (US4). Клиент MCP поставщика, инструмент `web_search`,
событие `sources`, правила разделения слоёв в промпте. Отключается отсутствием
ключа, поэтому срез снимается целиком, если что-то пойдёт не так.

## Complexity Tracking

| Усложнение | Зачем | Почему не проще |
|---|---|---|
| `langchain` + `langgraph` (+5 пакетов) | цикл «модель → инструмент → модель» и типизированные события с границами вызовов | руками это ~40 строк цикла плюс разбор кусков вызова, где имя приходит в первом куске, а аргументы дособираются в следующих. Отлаживать это за три дня до финала дороже зависимости |
| `langchain-mcp-adapters` (+2 пакета) | ходить к поставщику поиска по MCP | библиотека поставщика проще, но MCP-клиент — прямой ответ организаторам, сказавшим «видим решение как MCP-тул»: продукт оказывается по обе стороны протокола |
| Свой `web_search` поверх чужого `tavily_search` | схема поставщика стоит 890 токенов на каждом вызове, своя — около 60 | отдать их схему напрямую проще на одну функцию, но съедает 10 % минутной квоты на каждом вызове модели |

Итог по весу: **62 → 69 пакетов** в образе. Прирост измерен разрешением
зависимостей для linux/py3.12 на обеих версиях `pyproject.toml`.

## Что осталось за рамками

- **Сравнение нескольких контрагентов** — другой интерфейс, другая работа.
- **MCP-сервер продукта** — не трогаем, хотя фича делает продукт MCP-клиентом.
- **Платный ключ модели.** Кодом не решается. На бесплатном ключе второй вопрос
  подряд с инструментом упрётся в лимит — это записано в спеке как внешний риск
  и должно быть снято до защиты.
