# Implementation Plan: Графики в отчёте о контрагенте

**Branch**: `004-report-charts` | **Date**: 2026-09-04 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/004-report-charts/spec.md`

## Summary

Числа в разделах статичны: «Выручка 116 257 852 000 ₽» ничего не говорит о том, было
это в прошлом году вдвое меньше или вдвое больше. Пять графиков дают форму, число
остаётся рядом для точности.

Подход продолжает решение предыдущей фичи: **график собирается на сервере вместе
с отчётом и живёт внутри своего раздела.** Это не удобство, а следствие — разделы
уже упорядочены по наличию сигнала, значит график компании с миллиардными исками
окажется наверху сам, без отдельного правила. И модель в диалоге видит те же ряды,
что нарисованы на экране: спросить «что с выручкой» и получить расхождение с графиком
невозможно.

Интерфейс получает описание графика и рисует его компонентом дизайн-системы.
Решать, какие данные достаточны для графика, — доменное знание, и держать его копию
на клиенте значило бы разойтись с сервером.

## Technical Context

**Language/Version**: Python 3.12 (сборка описаний) · TypeScript 5.9 + React 18 (отрисовка)

**Primary Dependencies**: `@alfalab/core-components-chart` 5.0.10 — единственная новая.
Внутри использует recharts, то есть выбор дизайн-системы не отрезал полноценную
библиотеку, как выглядело при постановке вопроса

**Storage**: подготовленный набор из 200 контрагентов, ряды берутся из записи

**Testing**: pytest + ruff

**Target Platform**: десктопный браузер плюс печать

**Performance Goals**: отчёт открывается не позднее 2 секунд, как и до графиков

**Constraints**: график строится без обращения к модели; разброс величин от 1,9 млн ₽
до 279 млрд ₽ на одной оси не помещается, масштаб выбирается по данным; печать без
наведения мышью

**Scale/Scope**: 5 графиков, 200 контрагентов, до 3 точек в финансовом ряду
и до 4 в судебном

## Constitution Check

*GATE: пройден до Phase 0, перепроверен после Phase 1.*

| Принцип | Как соблюдается |
|---|---|
| **I. Спека — первична** | Спека написана и уточнена; состав и инструмент подтверждены пользователем |
| **II. Ядро не знает про протоколы** | Описания графиков собирает `core/charts.py` — чистая функция от записи. Ни HTTP, ни MCP. Отрисовка целиком в интерфейсе |
| **III. Минимальная реализация** | Одна новая зависимость, и та из дизайн-системы. Картинка для программных клиентов отложена: диалог инструментов не имеет, MCP не развёрнут |
| **IV. Требования кейсодателя — закон** | Графики названы обязательными и упомянуты трижды. Оценки риска не пересчитываются. Сравнение компаний на одном графике не вводится — ранжирование кейсодателю не нужно |
| **V. Отбор полей** | Ряды короткие: три точки по финансам, четыре по искам. В контекст модели уходит отчёт, а не сырые массивы — у самой тяжёлой компании 1744 производства |

**Structure Decision**: раскладка следует принципу II и решению предыдущей фичи.
Правило «когда данных достаточно для графика» — доменное знание наравне с «что важнее»:
две точки это ряд, одна — число. Держать его копию на клиенте значит гарантированно
разойтись с сервером, а вместе с ним и с тем, что видит модель.

## Complexity Tracking

| Отступление | Зачем нужно | Почему более простой путь отвергнут |
|---|---|---|
| Описания графиков собираются на сервере, а не в интерфейсе | Модель в диалоге получает те же ряды, что нарисованы. Иначе на вопрос «что с выручкой» ответ разойдётся с графиком на том же экране, и проверить его будет нельзя | Собирать на клиенте — держать вторую реализацию правила достаточности данных и следить, чтобы она не разъехалась. Ровно та ошибка, которую фича 003 уже исправляла |
