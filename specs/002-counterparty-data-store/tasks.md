# Tasks: Витрина данных контрагентов на сервере

**Input**: Design documents from `/specs/002-counterparty-data-store/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/](./contracts/)

**Tests**: включены. Конституция требует проверяемости каждой задачи и зелёного CI
(`ruff` + `pytest`) перед merge, а [data-model.md](./data-model.md) задаёт инварианты
набора, которые нельзя проверить глазами.

**Organization**: задачи сгруппированы по историям. Плоская выгрузка вынесена в US3,
а не в фундамент, — иначе история осталась бы без содержания, а её ценность (удвоение
данных) нельзя было бы поставить и проверить отдельно.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: можно делать параллельно — разные файлы, нет незакрытых зависимостей
- **[Story]**: к какой истории относится задача (US1, US2, US3)
- В описании указан точный путь к файлу

## Path Conventions

Веб-приложение: `src/core/` (доменная логика), `src/api/` и `src/mcp_server/`
(тонкие приложения), `src/web/` (интерфейс), `scripts/` (инструменты разработчика),
`tests/` в корне. Раскладка из [plan.md](./plan.md).

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: без зависимостей
- **Foundational (Phase 2)**: после Setup. **Блокирует все истории**
- **US1 (Phase 3)**: после Foundational
- **US2 (Phase 4)**: после Foundational. От US1 не зависит — другая ручка, другой путь
- **US3 (Phase 5)**: после Foundational. От US1 и US2 не зависит: расширяет набор, не трогая способ его отдачи
- **Polish (Phase 6)**: после историй, которые решено поставить

### User Story Dependencies

- **US1 (P1)**: самостоятельна. Даёт работающий продукт на ста контрагентах
- **US2 (P2)**: самостоятельна. Единственное пересечение с US1 — общий доступ к набору, уже готовый в фундаменте
- **US3 (P3)**: самостоятельна. Меняет только шаг сборки и приведение; ручки и интерфейс не трогает. Поэтому её можно ставить последней без переделок

### Within Each User Story

- Приведение перед сборкой набора, сборка перед отдачей, отдача перед интерфейсом
- Тесты пишутся до реализации и должны падать до неё
- История закрывается целиком до перехода к следующей

### Parallel Opportunities

- T002 параллельна T001
- В фундаменте: T005 и T007 — разные файлы тестов, идут параллельно с T004 и T006 соответственно
- В US1: T013 (MCP) параллельна T011–T012 (HTTP); T016 параллельна интерфейсным T014–T015
- В US2: T019 и T020 параллельны T018
- В US3: T025 параллельна T022–T024
- В Polish: T030, T031, T032 параллельны — разные файлы
- При наличии людей US1, US2 и US3 идут параллельно после фундамента

## Implementation Strategy

### MVP — только US1

1. Phase 1: Setup
2. Phase 2: Foundational — **блокирует всё остальное**
3. Phase 3: US1
4. **Остановиться и проверить**: раздел 4 quickstart на реальных ИНН
5. Показывать можно уже здесь: сто контрагентов с настоящими данными вместо примеров

### Инкрементальная поставка

1. Setup + Foundational → набор собирается, ядро его читает
2. US1 → отчёт по ИНН настоящий → **это MVP, его можно показывать**
3. US2 → поиск по названию → показывать
4. US3 → 200 контрагентов вместо 100 → показывать
5. Polish → чистка, документация, шаг деплоя

### Порядок при нехватке времени

US1 обязательна — без неё продукт показывает примеры. US2 и US3 независимы друг
от друга: если время кончается, US3 даёт больше (удвоение данных снимает риск
попадания в пустую половину на защите), US2 — удобство. Резать первой стоит US2.
