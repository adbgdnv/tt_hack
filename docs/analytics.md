# Analytics / MVP Measurement Spec

## 1. Назначение документа

Документ фиксирует, **что в текущем MVP действительно можно измерять, из каких данных это получается и какие продуктовые события пока не собираются централизованно**.

Analytics в текущей реализации не является отдельным telemetry-контуром. В продукте есть:

- серверные данные, из которых строится отчёт и расчёт продуктовых признаков;
- локальное состояние веб-интерфейса;
- техническая наблюдаемость LLM-вызовов;
- результаты AI-evaluation и regression-проверок.

При этом отдельного хранилища продуктовых событий, отдельного event API или аналитической SDK в текущем MVP нет.

Поэтому важно не смешивать:

1. **факты о контрагенте и производные показатели**;
2. **действия пользователя в интерфейсе**;
3. **технические данные о работе AI**;
4. **результаты offline / live evaluation**.

---

# 2. Источники аналитики

В текущем MVP используются четыре класса данных.

## 2.1. Raw / Data-derived

Показатели, которые рассчитываются напрямую из подготовленного набора данных контрагентов.

Используются для:

- проверки полноты и покрытия данных;
- построения структурированного отчёта;
- определения состояния разделов `SIGNAL`, `FILLED`, `EMPTY`, `NOT_APPLICABLE`;
- формирования факторов и межраздельных противоречий;
- расчёта собственного продуктового вердикта;
- сравнения нескольких контрагентов;
- построения финансовых, судебных и исполнительных графиков.

Источник:

**dataset → normalization → report / derived metrics**

Такие показатели характеризуют **контрагента и качество доступных данных**, а не поведение пользователя.

Ключевое правило:

**`EMPTY` ≠ `CLEAN`**

Отсутствие данных не превращается в нулевое значение и не трактуется как отсутствие риска.

---

## 2.2. Product State / Client-side behaviour

Интерфейс хранит ряд состояний, необходимых для пользовательского сценария, но в текущем MVP они **не отправляются в отдельную централизованную систему продуктовой аналитики**.

Фактически в клиенте присутствуют:

- поисковый запрос и результаты поиска;
- открытая компания;
- открытый раздел отчёта;
- режим `report` / `compare`;
- пул сравнения;
- история последних проверок;
- состояние AI-диалога;
- suggested questions и уже использованные вопросы;
- состояние обратной связи по AI-ответам;
- контекст сделки;
- состояние streaming-ответа;
- ошибки загрузки и ошибки AI;
- факт открытия / сворачивания AI-разбора.

История последних проверок хранится в `localStorage` браузера. Контекст диалога и feedback живут в состоянии текущего клиентского сеанса.

Следовательно, такие признаки **доступны приложению в runtime, но не образуют накопленную продуктовую аналитику между пользователями и сессиями**.

Источник:

**UI state → local runtime state / localStorage**

---

## 2.3. LLM / Technical Observability

Для LLM-вызовов есть отдельная техническая наблюдаемость.

Вызов модели выполняется через LangChain `ChatOpenAI`. При наличии соответствующей настройки трассировки вызов содержит metadata:

- `environment`;
- `inn`;
- `provider`;
- имя запуска `counterparty-chat`;
- количество входных и выходных токенов;
- фактически использованную модель.

Также в ответе LLM доступны:

- время и успешность вызова на уровне вызывающего контура;
- модель;
- `prompt_tokens`;
- `completion_tokens`;
- текст ответа.

Это позволяет анализировать прежде всего **качество, стоимость и техническое поведение AI**, но это не заменяет продуктовую событийную аналитику.

Источник:

**LLM request → LangChain / tracing → technical metrics**

---

## 2.4. Evaluation / Quality data

Отдельный класс данных — результаты проверки качества AI и доменной логики.

В репозитории есть regression/eval-контур для фиксированного набора кейсов, а также проверки:

- корректности числовых утверждений;
- groundedness относительно доступных данных;
- корректного отказа при недостатке данных;
- работы инструментов;
- поведения multi-turn диалога;
- обработки разных состояний разделов;
- согласованности отчёта и AI-ответа.

Эти данные используются для **quality gate**, а не как пользовательские product events.

Источник:

**eval case → model / agent run → evaluation result**

# 3. Общие требования к событиям

В текущем MVP централизованный event-трекер **не реализован**, поэтому перечисленные ниже параметры являются контрактом для будущей продуктовой аналитики, а не утверждением, что такие события уже собираются.

Для будущих product events рекомендуется фиксировать:

### Обязательные

- `event_name`
- `event_timestamp`
- `session_id`
- `user_id` или анонимизированный идентификатор
- `screen`
- `product_version`

### Контекстные

- `inn_hash` или иной безопасный идентификатор контрагента;
- `block_id`;
- `interaction_id`;
- `question_type`;
- `source`;
- `provider`;
- `model`;
- `error_code`;
- `deal_scheme`, если действие относится к контексту сделки;
- `compare_pool_size`, если действие относится к сравнению нескольких компаний.

Для AI-сценариев отдельно желательно различать:

- открытие AI;
- отправку вопроса;
- suggested question;
- начало и завершение tool call;
- переход к графику или источнику;
- feedback на ответ;
- abort / timeout / error;
- завершение пользовательского сценария.

### Что нельзя считать реализованной аналитикой

Наличие состояния в React само по себе не означает наличие метрики.

Например:

- `feedback` хранится в компоненте и не отправляется в analytics backend;
- история проверок хранится в `localStorage`;
- открытие блока не формирует централизованное событие;
- suggested questions вычисляются на клиенте, но usage rate не сохраняется;
- переход chat → block не образует накопленную воронку.

Поэтому текущие продуктовые метрики следует считать **проектными KPI**, пока не появится централизованный сбор соответствующих событий.

### Privacy / Data minimization

Сырые персональные данные и содержимое пользовательского сообщения не должны попадать в telemetry без отдельного основания.

Для контрагента в аналитике предпочтителен обезличенный идентификатор.

Для AI необходимо отдельно контролировать передачу:

- пользовательского текста;
- условий сделки;
- ИНН;
- технических metadata.

Технические AI-трейсы и продуктовая аналитика не должны автоматически становиться одним и тем же хранилищем.
