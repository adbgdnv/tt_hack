# От комментария к задаче

Как замечание превращается в правку кода и почему между ними всегда стоит
человек.

Собирает комментарии `vibe-debug` (`docs/VIBE-DEBUG-RUNBOOK.md`). Схема записи
одна: `schemas/vibe-debug-comment.schema.json`. Карточки разбора —
`docs/review/`.

## Правило

**Комментарий — это вход, а не задача.** Появление `DBG-*` не даёт права
менять код. Ни один агент не начинает правку по факту комментария.

Причина: замечания пишутся в свободной форме, вперемешку — формулировка,
сомнение, референс, продуктовое решение. Разбор отделяет одно от другого, а
человек решает, что из этого делаем.

## Конвейер

```text
DBG-*              комментарий в очереди, статус new
  │
  ├─ 1. снимок     read-only копия очереди + audit
  ├─ 2. разбор     карточка в docs/review/<дата>-<область>.md   ← агент
  ├─ 3. решение    строка «Решение:» в карточке                 ← только человек
  ├─ 4. промпт     готовый текст задания исполнителю            ← агент
  ├─ 5. правка     ветка, минимальное изменение                 ← исполнитель
  ├─ 6. проверка   тесты + превью на 375 и 1440
  └─ 7. resolved   статус через review API + строка в PR
```

Шаги 1–2 и 4 делает агент. Шаг 3 — только человек. Шаг 7 не выполняется, пока
правка не видна в том же превью, где оставили комментарий.

## Шаг 1. Снимок и аудит

Данные на сервере трогать нельзя: там чужие комментарии. Работаем с копией.

```bash
curl -s -u "$DEBUG_USER" \
  https://tt-hack-review.72.56.16.44.sslip.io/__review__/comments \
  | python3 -c 'import sys,json;json.dump(json.load(sys.stdin)["comments"],open("/tmp/review/comments.json","w"),ensure_ascii=False,indent=2)'
python3 scripts/audit_vibe_debug_data.py \
  --comments /tmp/review/comments.json \
  --attachments /tmp/review/attachments
```

Аудит должен вернуть `"ok": true`. Ошибки схемы — стоп. Предупреждения про
legacy-записи (`mode`, `anchor`, `attachments`, `displayAuthor`, `updatedAt`)
допустимы и не чинятся.

## Шаг 2. Разбор

```bash
python3 scripts/review_triage.py \
  --comments /tmp/review/comments.json \
  --out docs/review/2026-09-03-preview.md
```

Скрипт собирает механическую часть карточки — экран, объект, автора, viewport,
дословный текст, вложения, прямую ссылку — и оставляет пустыми поля, которые
надо думать. Повторный запуск дописывает только новые `DBG-*`.

### Классы

| Класс | Что это | Что делаем |
|---|---|---|
| `content` | формулировка, состав текста, название раздела | правим сразу после решения |
| `ux` | поведение блока, состав экрана, что после клика | предлагаем варианты, выбирает человек |
| `scope` | меняет объём работ или требования | предлагаем формулировку задачи, id выделяет человек |
| `question` | нельзя закрыть без ответа заказчика | фиксируем вопрос, код не трогаем |
| `bug` | сломано то, что должно работать | правим как обычный дефект |
| `fyi` | подтверждение или референс | сохраняем материал, закрываем без правки |

### Что обязательно в карточке

- **Что понято** — своими словами, в терминах экрана и файлов. Дословный
  пересказ комментария = разбор не сделан.
- **Что не понято** — честно. Пустое поле допустимо только там, где высказан
  факт, а не пожелание.
- **Затрагивает** — конкретные файлы. Сквозные части (`preview/assets/vibe-debug.*`,
  общая шапка/подвал страниц) называть отдельно: правка в них задевает все экраны.
- **Связки.** Комментарии часто отменяют друг друга. Пара, решаемая одним
  решением, помечается в обеих карточках.
- **Конфликты с принятым.** Если комментарий разворачивает закрытый вопрос —
  это `question`, а не `content`.

Чего в карточке быть не должно: догадок о продуктовом решении и правок, начатых
до строки «Решение».

## Шаг 3. Решение

Строку `Решение:` пишет человек. Формат:

```md
**Решение:** **принять** — dbndrnk, 2026-09-03. Плашку риска красим в --risk,
состав блока не трогаем.
```

Допустимо: `принять`, `принять с изменением` (и чем именно), `отклонить`
(и почему), `вопрос заказчику` (и какой). Пустая строка означает «работа не
начата», а не «делай на своё усмотрение». Если в карточке два варианта — в
решении называется один.

## Шаг 4. Промпт исполнителю

Промпт пишется в карточку и уходит субагенту как есть — он не видит ни очереди,
ни этого разговора.

Обязательные части:

1. **Задача** — одно предложение, что должно стать правдой.
2. **Вход** — id комментария, вложения как референс, не как макет.
3. **Список действий по файлам** — пронумерованный.
4. **Ограничения** — что нельзя: капслок, комментарии в коде, выдуманные цифры
   и тексты, спецсимволы руками.
5. **Проверка** — команды и ручные шаги.

Шаблон:

```text
Задача: <что должно стать правдой>.
Вход: комментарий <DBG-…>, вложения <ID> — референс, не макет.

Сделать:
1. <файл> — <изменение>
2. <файл> — <изменение>

Ограничения: капслок запрещён; комментариев в код не добавлять; цифры, цены и
тексты документов не выдумывать.

Проверка: python3 -m unittest discover -s tests зелёный (если трогали сервер);
<ручной шаг>; 375 и 1440 без горизонтального скролла.
```

### Декомпозиция на субагентов

По границе файлов, а не по числу пунктов.

- один субагент — один связанный набор файлов; два субагента не пишут в один
  файл одновременно;
- сквозной компонент (`vibe-debug.*`, общая шапка/подвал) — всегда отдельный
  субагент;
- карточки одной связки идут одному субагенту;
- `question` и `scope` субагентам не отдаются — там нечего исполнять.

## Шаг 5–6. Правка и проверка

```bash
git switch -c fix/<короткое-имя>
# правка
python3 -m unittest discover -s tests
```

Правка минимальная и по карточке. Если решение не закрывает случай — стоп и
обратно к человеку. Проверка обязательно включает превью на ширине из карточки.

## Шаг 7. Закрытие

```bash
curl -X POST "https://tt-hack-review.72.56.16.44.sslip.io/__review__/comments/status" \
  -u "$DEBUG_USER" -H 'Content-Type: application/json' \
  -d '{"id":"DBG-…","status":"resolved"}'
```

`resolved` — только после того, как правка видна в превью. Отклонённый
комментарий → `wont_fix` с причиной в карточке, не молча.

## Что хранится и где

| Что | Где | Кто пишет |
|---|---|---|
| сам комментарий | `comments.json` на сервере ревью | участники через оверлей |
| вложения | `attachments/` там же | они же |
| схема записи | `schemas/vibe-debug-comment.schema.json` | разработчик, одним коммитом с сервером и тестом |
| карточка разбора | `docs/review/<дата>-<область>.md` | агент, кроме строки «Решение» |
| решение | та же карточка, строка «Решение» | только человек |

Карточки версионируются вместе с кодом: через месяц видно не только что
поправили, но и почему решили именно так.
