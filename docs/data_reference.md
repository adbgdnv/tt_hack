# Данные: что обещано спекой и что лежит в выгрузке

Сверено 03.09.2026 по всем **200 компаниям** (100 из JSON + 100 из CSV) против
`data/GetFullReportResponse.md` — официальной спецификации полей от кейсодателя.

Источники: `data/GetFullReportResponse.md` (спека), `data/image_1.png` (карта рынка),
`data/image_2.png` (расшифровка светофоров), обе выгрузки. `data/` — симлинк на
`docs_alpha/` вне репозитория.

## 1. Светофоры — что они на самом деле значат

Расшифровка из `data/image_2.png`, прямые слова кейсодателя. **Это два разных
светофора от двух разных организаций**, и путать их нельзя.

### `baseInfo.riskLevel` — «Светофор»

> Цветовой индикатор, который рассчитывается **скорингом банка** на момент проверки по
> внутренней методологии, которая учитывает множество факторов и **модель не разглашается**.

| Значение | Смысл | Сколько из 200 |
|---|---|---:|
| `LOW` — зелёный | надёжный контрагент | 163 |
| `MEDIUM` — жёлтый | требует внимания | 26 |
| `HIGH` — красный | в зоне риска | 5 |
| `UNKNOWN` — серый | **нет данных для оценки** | 6 |

**`UNKNOWN` в спецификации не описан** — там только `LOW / MEDIUM / HIGH`. В данных он
есть у шести компаний. Обрабатывать обязательно, иначе шестёрка провалится в «иначе».

### `zskRiskLevel` — «ЗСК»

> Агрегация данных с платформы «Знай своего клиента» **ЦБ РФ** —
> <https://www.cbr.ru/counteraction_m_ter/platform_zsk/proverka-po-inn/>

| Значение | Сколько из 200 | Как выводится в их интерфейсе |
|---|---:|---|
| `GREEN` | 158 | Green |
| `YELLOW` | 40 | **grey** |
| `RED` | 2 | **grey** |

Последняя колонка — дословно из спецификации: `GREEN / YELLOW / RED (в интерфейс
выводится Green/grey/grey)`. А серый, по расшифровке выше, означает «нет данных для оценки».

**Отсюда следствие, на которое стоит опереться продуктом:** у 42 компаний из 200 (21%)
платформа ЦБ подняла флаг, но в текущем интерфейсе они выглядят ровно так же, как
компании без данных. Сигнал есть в данных и гаснет на выводе.

## 5. Ловушки

Каждая ломает наивную обработку молча, без исключения.

### CSV расплющен по максимальной длине массивов

CSV — это тот же JSON, развёрнутый нотацией `report.путь[i].подпуть`. Отсюда 2654
колонки: у одной компании **1744 исполнительных производства**, и `executionProceedings`
занимает 1693 колонки из 2654. Всего производств в выгрузке 5178, активные есть у 33 компаний.

**Действующий загрузчик это не разбирает.** `mocks._csv_row_to_report` режет ключ только
по точке и не понимает `[i]`, поэтому получает ключи с именами `finReports[0]` и
`positive[0]` вместо списков. Результат проверен: **все 100 CSV-компаний отдают только
название и ИНН** — ноль негативных факторов, ноль финотчётности, ноль арбитража. Ничего
не падает, `slim` честно возвращает `None`, и дыра не видна.

### CSV отдаёт всё строками

`yearsFromRegistration` — `int` в JSON и `str` в CSV. То же с `finReports[].common.year`
и всеми суммами. Приводить типы надо при загрузке, а не в местах использования.

### `{"$numberLong": "..."}` вместо числа

Всего 67 значений по 16 путям. Чаще всего — `finReports[].common.proceeds` (15 раз),
`assets.totalAssets` и `liabilities.totalLiabilities` (по 10). Есть и в арбитраже:
`arbitrationByStatus.commonAmount`, `dfAmount`, `arbitrationCases[].defendantAmount`.

Затрагивает ровно самые крупные значения — у ООО «МАКСМАРКЕТ» активы 279 815 832 000 ₽ и
выручка 116 257 852 000 ₽. `float()` на такой обёртке падает, и из выборки вылетают
именно тяжёлые случаи.

### Кириллическая «а» в коде фактора

Код `аrbitrationDefendant` среди **позитивных** факторов начинается с кириллической «а»
(U+0430). Среди негативных тот же по смыслу код записан латиницей. Сравнение строк
промахивается — проверено, других кодов с не-ASCII символами в выгрузке нет.

### `defandantArbitration` — опечатка в самой схеме

Должно быть `defendant`, написано `defandant`. Это опечатка кейсодателя, она есть и в
спецификации, и в данных, по всему файлу. Не исправлять — иначе разъедется с источником.

## 6. Репутационные факторы: шум к сигналу

На 200 компаниях: **217 негативных** факторов против **3 122 позитивных**.
Отношение **14,4 : 1**.

Негативных кодов 15, и хвост очень длинный:

| Код | Срабатываний |
|---|---:|
| `arbitrationDefendant` | 67 |
| `massOkved` | 45 |
| `executionProceedings` | 33 |
| `massAddress` | 24 |
| `fnsBlocking` | 18 |
| `profit` | 10 |
| `invalidRegistrationData` | 6 |
| `invalidAddress` | 5 |
| `massAuthpersons`, `invalidAuthpersonsData` | по 2 |
| `currentAssets`, `liquidationStatus`, `dishonestProvider`, `taxArrears`, `inspectionWithViolation` | по 1 |

Пять кодов срабатывают один раз на всю выгрузку. Отдельную обработку под них писать
незачем — достаточно общего пути с человеческим названием.

### У факторов есть готовый русский текст

Проверено на всех 200 компаниях: поле `name` заполнено у **всех 217 негативных
и 3122 позитивных** факторов и содержит готовое предложение по-русски.

```
arbitrationDefendant → «Есть арбитражные дела, в которых выступает в качестве
                        ответчика, что может указывать на наличие споров…»
```

Значит переводить коды не нужно — формулировки уже даны кейсодателем. Это снимает
и риск: своя редактура могла бы исказить смысл, а текст источника совпадает с тем,
что пользователь видит в их интерфейсе. Длина: медиана 248 символов, максимум 402 —
для карточки нужен отдельный короткий заголовок, для содержания хватает источника.

**Аномалия:** у одного фактора в поле `chapter` лежит его собственный код
`inspectionWithViolation` вместо названия раздела. Один раз на 200 компаний.
Нераспознанный раздел не должен отбрасываться молча.

**Поправка к нашим же записям:** `liquidationStatus` в источнике означает
**процедуру банкротства**, а не «предстоящее исключение из ЕГРЮЛ», как записано
в описании МАКСМАРКЕТА.

### Разделы отчёта уже заданы данными

У каждого фактора есть поле `chapter` — это готовая структура разделов, придумывать её не надо:

| `chapter` | Негативных | Позитивных |
|---|---:|---:|
| `arbitr` — суды | 32 | 68 |
| `reestrs` — реестры ФНС | 29 | 788 |
| `okved` — виды деятельности | 25 | 75 |
| `execproc` — исполнительные производства | 18 | 82 |
| `finance` — финансы | 7 | 136 |
| `manager` — руководство | 3 | 297 |
| `relatedComp`, `license`, `site`, `filials` | 0 | 83 |

*(разбивка по 100 компаниям из JSON)*

В разделе `reestrs` на 29 негативных приходится 788 позитивных. Показать их все — значит
утопить сигнал; отсюда продуктовый ход вычитанием: гасим непроизошедшее, показываем
произошедшее.

## 7. JSON против CSV — что в каждой выгрузке

Пересечение выборок **нулевое** и по ИНН, и по ОГРН: это 200 разных компаний, а не 100
в двух форматах. При этом выборки нарезаны одним фильтром — совпадают до единицы:

| | JSON | CSV |
|---|---|---|
| Компаний | 100 | 100 |
| ИП / юрлиц | 25 / 75 | 25 / 75 |
| Даты отчётов | 29.07 – 27.08.2026 | 29.07 – 27.08.2026 |
| Возраст, лет | 0–32, медиана 6 | 0–32, медиана 6 |
| Моложе трёх лет | 29 | 29 |
| Статус | все `CURRENT` | все `CURRENT` |

Значит наблюдение, снятое на одной выгрузке, переносится на вторую.

### Наполнение блоков, из 100 в каждой

| Блок | JSON | CSV |
|---|---:|---:|
| `baseInfo`, `reputationalRisks` | 100 | 100 |
| `foundersInfo`, `taxSystem` | 75 | 75 |
| `finReports` | 67 | 69 |
| `relatedCompanies` | 61 | 65 |
| `arbitrationCases` | 44 | 57 |
| `executionProceedings` | 53 | 43 |
| `inspections` | 30 | 29 |
| `phones` | 29 | 31 |
| `coefficient` | 19 | 28 |
| `licenses` | 9 | 13 |
| `procurements` | 8 | 9 |
| `branchesInfo` | 2 | 6 |
| **`arbitrationByStatus`** | **100** | **61** |

Последняя строка — разница представления, а не данных. JSON хранит пустые структуры
(`{"plaintiffArbitration": {"plaintiffArbitrationFinished": {}}}`), CSV пустые ячейки не
заполняет, и после разворачивания ключ исчезает. Оба написания значат «дел нет», и код
должен понимать оба.

### Технические различия

| | JSON | CSV |
|---|---|---|
| Форма | вложенная | плоская, `report.путь[i].подпуть` |
| Размер схемы | 14 ключей верхнего уровня | 2654 колонки |
| Числа | `int` | **строки** |
| Булевы | `False` | **`'false'`** — строка |
| Большие числа | `{"$numberLong": "…"}`, у 10 компаний | обычные строки, обёрток нет |
| Даты | `{"$date": "…"}` | обычные строки |
| Медиана записи | 9 803 символа | 9 437 |
| Максимум | **238 412** (ЛЕ МОНЛИД) | 68 317 |

**`$numberLong` и `$date` — артефакты выгрузки из MongoDB и встречаются только в JSON.**
В CSV они уже разрешены в текст. Распаковка обёрток нужна на JSON-ветке, приведение
строк к числам — на CSV-ветке.

### Ловушка на стыке: `'false'` истинно

CSV отдаёт булевы строками, а непустая строка `'false'` в Python истинна. В
`slim.py` стоит `active = [p for p in proceedings if p.get("active")]` — как только
разбор `[i]` заработает, **все** производства CSV-компаний посчитаются активными.
Сейчас не видно только потому, что список пуст.

Отсюда требование к нормализатору: разворачивать индексы **и** приводить типы одним
шагом. Починить только первое — значит заменить пустые данные на неверные.

### Что внутри содержательно

Отрасли на 200 компаниях: строительство зданий 23 · оптовая неспециализированная
торговля 14 · стройматериалы 15 · автозапчасти 8 · грузовой транспорт 6. Выборка
со строительным перекосом.

Самые тяжёлые случаи:

| Компания | Арбитраж | Производств | Светофоры | Источник |
|---|---:|---:|---|---|
| ООО «ЛЕ МОНЛИД» | 4,53 млрд ₽ | 1744 | `UNKNOWN` / `GREEN` | JSON |
| ООО «МАКСМАРКЕТ» | 3,00 млрд ₽ | 507 | **`LOW` / `GREEN`** | JSON |
| ООО «УТС ТЕХНОНИКОЛЬ» | 2,18 млрд ₽ | 83 | `UNKNOWN` / `GREEN` | CSV |
| АО «ЭНЕРГОСПЕЦМОНТАЖ» | 1,70 млрд ₽ | 459 | `UNKNOWN` / `GREEN` | CSV |
| ООО «АЛЬЯНСТЕЛЕКОММУНИКЕЙШНС» | 1,51 млрд ₽ | 97 | **`LOW` / `GREEN`** | CSV |

## 8. Что из этого следует

- **Нормализатор — первая задача.** Пока `[i]` не разбирается, половина базы пустая, и
  любой слой поверх строится на дыре.
- **Отчёт можно собрать без ИИ.** Разделы заданы полем `chapter`, светофоры и негативные
  факторы есть у всех, временные ряды для графиков лежат готовыми. Модель не нужна ни
  для одного из этих шагов — значит отчёт не может ничего выдумать и не зависит от того,
  жив ли провайдер на демонстрации.
- **Графики строятся по наличию ряда, а не по решению модели.** `finReports` — 68%,
  `arbitrationCases` — 50%, `coefficient` — 23%. Нет ряда — честная строка вместо
  пустого графика.
- **`UNKNOWN` и серый ЗСК — не «нет риска».** Это «оценить нельзя», и формулировать надо
  именно так.
- **Ненулевой ЗСК гаснет в их интерфейсе.** 42 компании из 200 несут флаг ЦБ, который
  пользователь не видит. Показать его — самостоятельная ценность, ничего не выдумывая.

## Как воспроизвести

```bash
python3 scripts/audit_data.py           # покрытие каждого поля спеки + ловушки
python3 scripts/audit_data.py --traps   # только светофоры, факторы, $numberLong, типы

python3 scripts/build_dataset.py        # собрать набор из обеих выгрузок
pytest tests/test_dataset_integrity.py  # инварианты на собранном наборе
```

Сверка идёт по исходным выгрузкам, инварианты — по собранному набору. Второе ловит
то, что первое поймать не может: расхождение между исходником и результатом сборки.
Например, перевёрнутый признак активности производства выглядит как обычные данные,
и виден только сравнением доли с исходником.

Скрипт разворачивает CSV корректно, с разбором индексов `[i]`. Если кейсодатель
пришлёт новую выгрузку — перепроверять этим скриптом, а не глазами: все цифры выше
получены им.
