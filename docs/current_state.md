# Текущее состояние решения

**Проект:** агент и MCP-сервис для проверки контрагента в бизнесе  
**Статус:** рабочий MVP

## 1. Краткая аннотация

Проект представляет собой веб-сервис для интеллектуальной проверки контрагента перед началом или продолжением деловых отношений.

Пользователь ищет компанию по ИНН, названию или ФИО руководителя и получает структурированный отчёт по восьми направлениям: регистрация, суды, исполнительные производства, финансы, реестры, деятельность, руководство и связанные организации. Поверх отчёта работает AI-диалог, который объясняет данные и отвечает на вопросы пользователя.

Архитектурный принцип — **LLM не является источником фактов**. Модель работает с тем же подготовленным отчётом, который видит пользователь, а отсутствие данных явно отделено от отсутствия риска.

В текущей версии реализованы собственный вердикт по открытым данным, контекст сделки, сравнение нескольких контрагентов без числового score, финансовые и судебные графики, внешний news-пайплайн и MCP-интерфейс. Решение работает на подготовленной выборке из **200 контрагентов**.

---

## 2. Проблематика

Большой отчёт по юридическому лицу сложно быстро интерпретировать: значимые сигналы теряются среди нейтральной информации, несколько компаний приходится сравнивать вручную, а отсутствие данных легко принять за отсутствие риска.

Задача решения — сократить путь от поиска контрагента до понимания того, что действительно требует внимания, и дать пользователю быстрый интерфейс для уточняющих вопросов.

---

## 3. Постановка задачи

Решение должно:

1. находить контрагента и собирать единый отчёт;
2. выделять значимые сигналы и противоречия между разделами;
3. корректно различать `SIGNAL`, `FILLED`, `EMPTY` и `NOT_APPLICABLE`;
4. отвечать на вопросы пользователя на основе доступных данных;
5. учитывать контекст сделки: сторона, схема расчётов, сумма и срок;
6. поддерживать анализ нескольких контрагентов без искусственного рейтингового score;
7. предоставлять программный доступ через MCP;
8. показывать внешние источники отдельно от основного отчёта.

Агент не заменяет банковскую оценку риска и не пытается воспроизводить внутреннюю методику банка. Его задача — объяснять доступные данные, сворачивать сложный отчёт и показывать, что требует внимания.

## 4. Техническое решение

```text
React / TypeScript
        │
        ▼
     FastAPI
        │
        ├── Agent / LLM
        ├── News pipeline
        └── Core domain logic
                ├── normalization
                ├── repository
                ├── report
                ├── factors / triggers
                ├── compare
                ├── deal context
                └── charts / data slimming

MCP server ───────────────► Core
```

Бизнес-логика сосредоточена в `core/`, а API, AI-агент и MCP выступают адаптерами. Единый `Report` используется веб-интерфейсом, AI-диалогом и MCP, что снижает риск расхождения между тем, что видит пользователь, и тем, что объясняет модель.

Для дополнительных действий агент использует серверные инструменты: построение графиков, lookup по доступным данным, проверку утверждений и работу с подготовленными источниками. В pooled-сценарии инструменты, завязанные на одиночный UI-контекст, ограничиваются отдельно.

---

## 5. Работа с данными

```text
JSON + CSV → normalize → единая структура → dataset → Report
```

Нормализация восстанавливает вложенные структуры и типы, обрабатывает MongoDB-обёртки `$numberLong` и `$date`, плоские индексированные поля и типизацию boolean-значений.

Подготовленный набор содержит **200 контрагентов** и загружается в память при старте. Исходный dataset не хранится в публичном репозитории из-за чувствительных данных.

Используется in-memory repository, достаточный для MVP. Архитектурный интерфейс позволяет позднее заменить хранилище без изменения основной бизнес-логики и API.

## 6. Реализованные компоненты

### Структурированный отчёт

`core/report.py` формирует восемь разделов и приводит разрозненные источники к единому виду.

Состояния:

- **SIGNAL** — есть сигнал, требующий внимания;
- **FILLED** — данные присутствуют;
- **EMPTY** — данных нет;
- **NOT_APPLICABLE** — раздел неприменим.

Принцип: **«нет данных» не равно «риска нет»**.

### Факторы и противоречия

Факторы описывают значимость отдельных сигналов. Дополнительно `triggers.py` выявляет межраздельные противоречия, которые не видны из одного поля: например, тяжёлые публичные признаки при спокойных внешних индикаторах, негативный собственный капитал, несоразмерность требований к выручке и другие комбинации.

### Собственный вердикт

`verdict.py` формирует независимый взгляд на открытые данные в трёх основных уровнях: **вопросов нет**, **есть вопросы**, **осторожнее**. При недостаточности данных используется состояние **«оценить нечем»**. Вердикт основан на тех же разделах и весах факторов, что и основной отчёт, и не является банковским score.

### Сравнение контрагентов

`core/compare.py` сравнивает до 8 компаний по одинаковым сигналам, состояниям и индикаторам. Результат — не числовой рейтинг, а порядок проверки и рекомендации: где меньше вопросов, а где требуется больше внимания.

### Контекст сделки

`core/deal.py` учитывает роль компании в сделке, схему расчётов, сумму, срок и цель. Контекст сделки влияет на интерпретацию, но пользовательские вводные не записываются как факты отчёта.

### AI-агент

Агент построен на LangChain/LangGraph и работает через OpenAI-compatible LLM API. В модель передаётся подготовленный отчёт, история диалога и вопрос пользователя.

```text
SYSTEM PROMPT + REPORT + HISTORY + USER QUESTION
```

История ограничивается последними ходами; при смене компании она очищается, при этом контекст сделки сохраняется. Поддерживаются обычный и streaming-режимы ответа, а также pooled-сценарий для сравнения компаний.

### Графики и внешние источники

`charts.py` формирует графики по финансовым, судебным и исполнительным данным. Пропуски не заменяются нулём, а одной точке не приписывается ложная динамика.

Отдельный news-пайплайн выполняет поиск внешних публикаций, чтение найденных страниц и их классификацию. Внешние сведения отделены от основного отчёта и сопровождаются источниками.

### FastAPI и веб-интерфейс

Backend предоставляет поиск, получение отчёта, обычный и streaming chat, сравнение компаний, новости и health check. Frontend построен на React + TypeScript.

Основной пользовательский путь:

```text
Поиск → Контрагент → Отчёт → Сигналы → AI-ответ
```

### MCP

MCP работает как адаптер над `core`. Реализованы инструменты:

- `search_counterparty`;
- `get_counterparty_report`;
- `assess_risk`;
- `find_contradictions`;
- `compare_counterparties`;
- `get_financials`;
- `look_up`;
- `verify_claims`;
- resource `counterparty://{inn}`.

## 7. Полученные результаты

Текущая версия даёт полный end-to-end сценарий: **поиск → структурированный отчёт → сигналы и противоречия → AI-объяснение**.

Ключевые результаты:

- единый отчёт из восьми разделов для 200 контрагентов;
- явное разделение сигнала, заполненных данных, пустых данных и неприменимости;
- собственный вердикт по открытым данным без числового рейтинга;
- сравнение нескольких компаний по единому набору признаков;
- контекст сделки в AI-диалоге;
- streaming-ответы и история диалога;
- финансовые, судебные и исполнительные графики;
- отдельный pipeline внешних новостей;
- MCP-интерфейс с набором инструментов для программного доступа;
- автоматизированные тесты и проверки качества AI-сценариев.

---

## 8. Ограничения

- **Демо-датасет:** текущая версия работает на подготовленной выборке и не подключена напрямую к актуальным банковским источникам.
- **Нет транзакционных сигналов:** решение не видит поведение по операциям и не может объяснять внутреннюю методику банковского риск-скоринга.
- **Нет эталонного датасета ответов:** качество контролируется собственным live-eval, без полноценного gold/reference набора.
- **Производительность сравнения:** пул из 3 компаний сейчас обрабатывается примерно за **60 секунд**.
- **In-memory sessions:** история чатов хранится внутри процесса и пока не рассчитана на горизонтальное масштабирование.
