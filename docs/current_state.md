# Текущее состояние решения

**Проект:** Создание агента и MCP-сервера для проверки контрагента в бизнесе  
**Статус:** рабочий прототип / MVP в активной доработке

---

## 1. Краткая аннотация

Проект представляет собой веб-сервис для интеллектуальной проверки контрагента на основе данных отчёта о юридическом лице.

Пользователь вводит ИНН или поисковый запрос, получает карточку контрагента и структурированный отчёт по ключевым направлениям: регистрация, судебные дела, исполнительные производства, финансы, реестры, деятельность, руководство и связанные организации. Поверх этого отчёта работает AI-диалог.

Ключевой принцип — **LLM не должна придумывать данные**. Модель получает тот же подготовленный отчёт, который видит пользователь, и отвечает только на его основе. Отсутствие данных явно отличается от отсутствия риска.

Текущая версия работает на подготовленном наборе из **200 контрагентов**, имеет веб-интерфейс, FastAPI backend, слой доменной логики, LLM-интеграцию, базовый MCP-сервер и автоматизированные тесты.

---

## 2. Проблематика

Исходный продукт содержит большой объём регистрационной, финансовой, судебной и иной информации. По мере расширения отчёта растёт когнитивная нагрузка на пользователя:

- важные сигналы теряются среди нейтральной информации;
- несколько компаний приходится анализировать вручную;
- отсутствие данных легко спутать с отсутствием риска;
- не хватает быстрого способа задать вопрос по открытому отчёту.

Цель решения — сократить путь от поиска контрагента до понимания основных рисков и повысить удобство работы с продуктом.

---

## 3. Актуальная постановка задачи

Решение должно:

1. получать данные о контрагенте из доступного набора;
2. формировать единое структурированное представление отчёта;
3. выделять области, требующие внимания;
4. отвечать на уточняющие вопросы в свободной форме;
5. использовать только входные данные и явно сообщать об их недостаточности;
6. предоставлять понятный веб-интерфейс;
7. по возможности поддерживать работу с несколькими контрагентами;
8. иметь MCP-интерфейс для программного доступа.

Собственный независимый скоринг не является целью: банковская оценка риска рассматривается как источник истины, а задача агента — объяснять и сворачивать доступную информацию.

## 4. Техническое решение

```text
React / TypeScript
      │
      ▼
FastAPI
      │
      ├── Agent / LLM
      └── Core domain logic
              ├── normalization
              ├── repository
              ├── report
              ├── factors
              └── data slimming

MCP server ───────────────► Core
```

Основной принцип: бизнес-логика находится в `core/`, а API, агент и MCP выступают тонкими адаптерами. Одно представление данных используется веб-интерфейсом, AI-диалогом и MCP.

---

## 5. Работа с данными

Исходные выгрузки сначала нормализуются:

```text
JSON + CSV → normalize → единая структура → dataset/
```

Pipeline восстанавливает вложенные структуры и типы, обрабатывает MongoDB-обёртки `$numberLong` и `$date` и исключает ошибки интерпретации строковых boolean-значений.

Набор содержит около **200 контрагентов** и загружается в память при старте. Dataset не хранится в публичном репозитории из-за чувствительных персональных данных.

Используется in-memory repository: для текущего объёма он достаточен, при этом интерфейс repository позволяет позднее заменить хранилище без изменения API и бизнес-логики.

## 6. Реализованные компоненты

### Структурированный отчёт

`core/report.py` формирует восемь разделов: регистрация, суды, исполнительные производства, финансы, реестры, деятельность, руководство и связанные организации.

Используются состояния:

- **SIGNAL** — есть сигнал, требующий внимания;
- **FILLED** — данные присутствуют;
- **EMPTY** — данных нет;
- **NOT_APPLICABLE** — раздел неприменим.

Ключевое правило: **«нет данных» не равно «риска нет»**.

### Факторы риска

Реализован словарь из **15 негативных кодов факторов**. Текст объяснения берётся из исходного поля `name`, что снижает риск расхождения с бизнес-формулировками кейса.

### Сжатие данных для LLM

`slim.py` оставляет для модели только релевантную часть отчёта. По измерениям проекта медианный контекст сокращается примерно с **3 268 до 257 токенов**, а P90 — с **7 065 до 385**.

### AI-агент

Используется OpenAI-compatible API с настройкой через `LLM_PROVIDER`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`. Основной сценарий рассчитан на Groq и `openai/gpt-oss-20b`.

Контекст:

```text
SYSTEM PROMPT + REPORT + HISTORY + USER QUESTION
```

Модель не получает tools для самостоятельного поиска: она объясняет только подготовленный сервером отчёт. История ограничена последними ходами и сбрасывается при смене контрагента.

### FastAPI и веб-интерфейс

Реализованы health check, поиск, получение компании и отчёта, AI-чат. Frontend построен на React, TypeScript, Vite и Alfa Core Components.

Основной пользовательский путь:

```text
Поиск → Контрагент → Отчёт → Сигналы и риски → AI-ответ
```

Убраны зашитые AI-ответы, жёстко заданный ИНН и интерфейсные сценарии, для которых ещё нет backend-реализации.

### MCP

Реализованы базовые инструменты:

- `search_counterparty`;
- `get_counterparty_report`.

MCP работает как адаптер над `core`.

### Тестирование

Автотесты покрывают нормализацию, целостность данных, repository, факторы, отчёт, slim-слой и AI-агента. Последний зафиксированный прогон: **89 тестов, lint без ошибок, frontend собирается**.

## 7. Предварительные результаты

- Подготовлен единый pipeline для JSON и CSV без потери типов.
- Исправлена проблема со строковыми boolean-значениями в CSV.
- Пользователь получает структурированный отчёт вместо необходимости просматривать весь исходный объём данных.
- AI корректно извлекает значения из отчёта, сообщает об отсутствии данных и не выдаёт категоричный вердикт без достаточных оснований.
- Реализован основной end-to-end сценарий от поиска до AI-уточнения.

## 8. Что пока не завершено

### Финансовая аналитика

`financials.py`, `compare.py` и `charts.py` содержат незавершённую backend-реализацию. Не доведены до финала расчёты финансовых коэффициентов, сравнение компаний и полный pipeline графиков.

### Расширенный MCP

Планировались `assess_risk`, `compare_counterparties`, `get_financials`, resource `counterparty://{inn}` и дополнительные prompts. Часть компонентов пока остаётся заглушками.

### Сравнение контрагентов

Продуктовая постановка допускает сравнение нескольких компаний, но полноценный механизм ещё не реализован. При этом отдельный рейтинговый score не является обязательным.

---

## 9. Ограничения

- Решение работает на подготовленной тестовой выборке и не подключено напрямую к боевым банковским источникам.
- Качество AI зависит от внешнего LLM-провайдера; нужен дополнительный benchmark контрольных вопросов.
- История чата хранится в памяти процесса, что подходит для MVP, но не для горизонтального масштабирования.
- Deployment ориентирован на защищённый серверный контур и демонстрационный сценарий.
- Полный MCP пока не завершён.

## 13. Итоговый статус

Проект уже представляет собой **работающий end-to-end MVP**, а не статический прототип:

```text
данные → нормализация → repository → структурированный отчёт
                                      ↓
                              FastAPI / AI / Web / MCP
```

Главная ценность — выстроенный контур доверенного анализа:

**источник данных → единый отчёт → тот же отчёт для пользователя и модели → ответ без выхода за границы данных.**

Основной разрыв до финальной версии находится в расширении аналитики — финансовых расчётах, графиках, сравнении и полноценном MCP — после чего необходимы финальный benchmark AI и сквозная приёмка.
