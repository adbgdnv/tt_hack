# Реестр рисков

Актуализировано 07.09.2026 по коду и документации репозитория. Методология —
реестр рисков: вероятность и влияние по шкале 1–3 (низкая/средняя/высокая),
оценка = произведение, приоритет: 1–2 низкий, 3–4 средний, 6–9 высокий.
Статус: открыт / частично смягчён / смягчён.

## Детали высокоприоритетных рисков

### R6 — Передача персональных данных зарубежным провайдерам
**Описание.** В промпт агента и в трассировку LangSmith уходят ФИО руководителей
и ИНН учредителей контрагентов (`.env.example:35-36`, `core/llm.py`). Провайдеры
(OpenRouter, Groq, LangSmith) — зарубежные сервисы. Явного согласия/анонимизации
нет, решение принято как компромисс ради качества отладки.
**Влияние.** Для реального банковского продукта — потенциальное нарушение 152-ФЗ
(трансграничная передача ПДн) и репутационный риск.
**Рекомендация.** Явно разграничить: для демо/хакатона — оставить как есть, но
задокументировать как временное решение; для production-контура — маскирование
ПДн перед отправкой в LLM либо отдельный on-prem/RU-хостинг модели.

### R8/R9/R10 — Единственный периметр защиты
**Описание.** Все три сервиса (`api`, `mcp`, `web`) публикуются наружу только
через nginx с Basic Auth на один общий логин/пароль; сами контейнеры слушают
`127.0.0.1`, но фаервол на сервере выключен (`docker-compose.yml:76-78`).
MCP-сервер вообще не имеет проверки идентичности вызывающего.
**Влияние.** Любая случайная смена `127.0.0.1:PORT` на `0.0.0.0:PORT` в
compose-файле немедленно открывает ФИО/ИНН всему интернету без второго рубежа
защиты. Прецедент почти произошёл: MCP уже спроектирован слушать `0.0.0.0`
внутри контейнера.
**Рекомендация.** Добавить сетевой уровень (ufw/security group) как второй
барьер, не полагаться только на biding+auth; для MCP — минимум токен в
заголовке при переходе к публичному доступу.

### R3 — Непроверяемые расчётные утверждения агента
**Описание.** Сверка чисел исключена из `/chat` намеренно (`main.py:368-374`):
по замерам она давала ложные срабатывания на процитированных числах и
пропускала часть выдуманных при расчётах. Проверка осталась только в
`verify_claims` MCP-инструменте, который вызывающий должен запросить сам.
**Влияние.** Обычный пользователь веб-интерфейса получает посчитанные агентом
величины (например, соотношение сумм) без автоматической проверки.
**Рекомендация.** Зафиксировать это ограничение в пользовательском интерфейсе
(дисклеймер у расчётных величин) либо вернуть частичную проверку с меньшим
числом ложных срабатываний.

## Ограничения самого реестра
Оценки вероятности/влияния — экспертные, основаны на анализе кода и
документации, а не на инцидентах. Часть рисков (R6, R8–R10) осознанно
допустима для хакатон-демо и требует пересмотра только при переходе к
production-контуру с реальными данными.
