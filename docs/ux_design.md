## User flow
— экран за экраном: ввод ИНН → дашборд с блоками → AI-разбор блока → диалог с пруф-виджетами → сравнение. Это прямое отражение progressive disclosure из твоего видения.

## Детальное описание экранов

### A. Главная / Поиск

**Назначение:** точка входа; максимально снизить барьер запуска проверки.

**Элементы:**
- **Умное поле поиска** — принимает ИНН, название компании или ФИО гендиректора. Автоподсказки из словаря; выбор подставляет корректный ИНН. *(H8/онбординг: пользователю не нужно знать ИНН наизусть.)*
- **История прошлых запросов** — карточки (название, ИНН, банковский риск, дата), клик → открывает отчёт (retention-хук).
- **Empty state (первый визит):** короткий онбординг в сервис, приглашение ввести ИНН, возможность сразу открыть чат.

**Состояния:**
| Состояние | Что показываем |
|---|---|
| Первый визит (нет истории) | Онбординг + подсказка ввода + вход в чат |
| Есть история | Список прошлых проверок |
| Идёт поиск | Inline-лоадер под полем |
| Найдено | → переход к B |
| Не найдено (см. ниже) | Inline-сообщение под полем |

**Связь:** H8 (онбординг), retention (история).

---

### A-inline. Результаты поиска (заменяют/дополняют подсказки прямо под полем)


**Логика:**
1. Ищем в **локальной базе** → найдено → открываем дашборд.
2. `[V2]` Если нет — fallback-запрос в **ЕГРЮЛ**:
   - **Есть в ЕГРЮЛ** → ставим запрос на обновление локальной базы; показываем inline: «Данные обновляются, ~N мин» + кнопка **«Уведомить по готовности»**. По готовности → дашборд.
   - **Нет в ЕГРЮЛ** → inline: «Компании по этому ИНН не существует» + приглашение ввести другой ИНН.

**MVP-упрощение (хакатон):** только шаг 1 (лок. база: найдено/не найдено inline). Шаги с ЕГРЮЛ — помечены `[V2 / цель-максимум]`.

**Связь:** H4 (честность про существование/отсутствие), robustness.

---

### B. Дашборд контрагента

**Назначение:** главный экран — за секунды дать «на что смотреть» + вход в объяснение.

**Элементы:**
- **Шапка:** название, ИНН, статус (действ./ликвид.), **банковский светофор** (source of truth, не пересчитываем), дата расчета.
- **Блоки** (регистрация, финансы, суды, исп. производства, реестры и т.д.), у каждого:
  - **мини-индикатор риска** — производный от фактов блока, **явно помечен как ориентир, не банковская оценка** (тултип «ориентир на основе данных блока»).
  - вид **⚪ «нет данных»** для пустых блоков.
- **Панель чата (справа):** саммари 1 абзац + 3 контекстных вопроса.
- **Действия:** 💾 PDF, 🔗 постоянная ссылка, ＋ сравнить `[TBU]`.

**Состояния:**
| Состояние | Что показываем |
|---|---|
| Загрузка отчёта | Скелетон-лоадер блоков (из UI-библиотеки) |
| Блок с данными | Мини-индикатор + превью |
| Блок без данных | ⚪ + «данных недостаточно» |

**Связь:** H1 (скорость/иерархия), H6 (виджеты), H7 (входы в разбор), guardrail (светофор не трогаем).

---

### B1. Диалог с ИИ (панель чата)

**Назначение:** объяснение и доверие; закрытие квалификационного разрыва.

**Элементы:**
- **Стартовое саммари** (1 абзац) при открытии дашборда.
- **3 контекстных предложенных вопроса** — генерятся по наиболее рискованным элементам компании; помогают онбордингу.
- **Ответ ИИ с пруфами:**
  - **мини-дашборд из блоков прямо в окне чата** — цифры показываются как виджеты, а не текстом *(гипотеза: пользователь доверяет цифрам-виджетам больше, чем числам в тексте — это уточнение H2/H9)*.
  - из пруфа можно **развернуть соответствующий блок** (открыть C).
  - структура: факт / интерпретация / чего не хватает / что проверить.
  - честное «недостаточно данных» + обходное решение + косвенные признаки.
- **Память в пределах сессии.**
- **Loading:** органичный стриминг ответа (лоадер из UI-библиотеки).

**Динамика вопросов:**
- При **открытии блока C** в чат добавляются **3 новых вопроса по этому блоку**:
  - если переписки ещё не было → **базовые** вопросы по блоку, связанные с обнаруженными рисками;
  - если переписка была → вопросы **таргетированные** под контекст диалога.

**Связь:** H2/H9 (пруфы-виджеты), H8 (контекстные вопросы), H4 (честность), H7 (связка с блоком).

---

### C. Блок-модал (всплывает поверх дашборда)

**Назначение:** глубокий разбор одного блока без ухода с дашборда.

**Элементы:**
- Подробные данные блока.
- **AI-разбор рисков внутри блока** (отдельный участок модала) — риски **профильные для типа блока** (юр.риски у юридического, финансовые у финансового и т.д.).
- Ссылки на материалы/источники.
- Кнопки: закрыть → вернуться к дашборду; открыть другой блок.

**Ключевое поведение (уточнение от тебя):**
- Открытие блока **НЕ пишет ничего в чат** сразу; AI-анализ живёт **внутри модала**.
- Вместо этого в чат-панель подставляются **3 новых вопроса** (base/targeted — см. B1).

**Состояние C-empty (нет данных):**
- Явно: «данных недостаточно».
- **Обходное решение** (если есть).
- Предложение **проверить связанные, косвенно говорящие об этом признаки**.

**Связь:** H7 (per-block разбор), grounding, **H4 (критично — no-data вид)**.

---

### D. Сохранить вид отчёта

- 💾 **PDF** — снимок дашборда.
- 🔗 **Постоянная ссылка** — для возврата/шэра (retention-хук).

### E. Сохранить чат

- 🔗 **Постоянная ссылка** на диалог.
- 📄 **.txt** — лог диалога.

### F. Режим сравнения — `[TBU]`

Отложено по твоему решению. Держим точку входа (＋ сравнить) как заглушку.

## Информационная архитектура дашборда 
— какие блоки, в каком порядке, где кнопки «AI-разбор», где риск-светофор.
## Wireframes / прототип
 — сначала low-fi (набросок), потом при наличии времени — интерактивный прототип (для теста H1/H7/H8 на пользователях ещё до финального кода).
## Дизайн ключевых виджетов
 — риск-карточка, финансовый график, матрица сравнения, пруф-виджет (цифра+ссылка на блок+источник). Эталон визуализации у вас уже есть — тот пример аналитики по 8 компаниям.
## Content design для ответов ИИ
 — как выглядит структура ответа: факт / интерпретация / чего не хватает / что проверить. Это фиксируется как шаблон/контракт ответа, а не отдаётся на волю LLM.
