# UX / MVP Design Spec

## 1. Назначение документа

Документ фиксирует, **как продукт выглядит и работает для пользователя на уровне MVP**.

Основная задача UX:

> превратить большой статичный отчёт о контрагенте в понятный интерактивный сценарий, в котором пользователь быстро видит значимые сигналы, может постепенно углубляться в данные и при необходимости получать объяснения через AI.

UX должен поддерживать ключевые продуктовые принципы:

- пользователь не должен самостоятельно собирать картину из десятков полей;
- информация приоритизируется по значимости для взаимодействия с контрагентом;
- порядок основных блоков одинаков для всех контрагентов;
- внутри блоков состав и представление данных могут меняться в зависимости от конкретного контрагента;
- пользователь сначала видит кратко считываемую информацию и только затем углубляется в детали;
- банковский risk signal отображается как исходный сигнал и не пересчитывается продуктом;
- AI не принимает решение за пользователя;
- AI объясняет доступные данные и помогает интерпретировать сложные показатели;
- отсутствие данных явно отличается от нормального состояния;
- существенные AI-утверждения должны быть связаны с доступным фактом или блоком.

# 2. UX Principles

## 2.1. From report to understanding

Пользователь не должен читать отчёт последовательно.

Вместо этого продукт должен обеспечивать:

**что важно → насколько это существенно → что именно это означает → где посмотреть детали.**

На первом экране пользователь должен получить быстро считываемую картину ситуации.

## 2.2. Progressive disclosure

Большой объём данных раскрывается по уровням:

**summary → block → detail → explanation → evidence**

При этом возможны разные пути:

**summary → block → detail → AI explanation**

или:

**summary → AI explanation → block → detail**

Внутри блока также могут существовать подблоки и дополнительные уровни детализации.

Цель — не скрывать данные, а **дозировать их представление**, чтобы пользователь не сталкивался сразу со всем объёмом исходного отчёта.

## 2.3. Consistent information architecture

Основные блоки и их порядок **не меняются от одного контрагента к другому**.

Меняться могут:

- значения;
- показатели;
- статусы;
- наличие сигналов;
- состав подробных данных внутри блока;
- дополнительные подблоки.

Постоянная структура необходима, чтобы пользователь запоминал расположение информации и быстрее ориентировался при повторных проверках.

## 2.4. Explainability first

AI не должен быть «магическим чатом».

Каждое существенное утверждение должно быть связано с доступным фактом и давать пользователю возможность перейти к соответствующему месту в отчёте.

## 2.5. No decision substitution

Интерфейс не должен формировать окончательный вывод за пользователя.

Задача UI:

- подсветить важные моменты;
- показать их **значимость и направление этой значимости**;
- объяснить, что именно стоит обратить внимание;
- дать доступ к фактам.

Пользователь самостоятельно принимает решение о дальнейшем взаимодействии с контрагентом.

## 2.6. Directional significance

На первом экране пользователь должен сразу понимать не только **насколько значим сигнал**, но и **в каком направлении он влияет на восприятие контрагента**.

Для каждого блока допускается компактное визуальное обозначение:

- **позитивная значимость** — фактор поддерживает положительную оценку;
- **нейтральная значимость** — существенного влияния не выявлено;
- **негативная значимость** — фактор требует внимания;
- **высокая негативная значимость** — фактор потенциально существенно влияет на способность контрагента выполнять обязательства;
- **недостаточно данных** — полноценная оценка невозможна.

Конкретные цвета и визуальные токены должны быть согласованы с design system, но направление сигнала должно считываться с первого взгляда.

## 2.7. Neutral risk framing

Продукт не должен фокусироваться исключительно на негативе.

Оценка и визуальная иерархия должны помогать увидеть:

- позитивные сигналы;
- нейтральное состояние;
- негативные сигналы;
- недостаток данных.

Ключевой критерий приоритизации — **значимость признака для способности контрагента выполнять обязательства**, а не просто его позитивность или негативность.

## 2.8. Explicit user action

Никакие существенные действия не должны происходить без явного намерения пользователя.

Например:

- ссылка AI на блок не должна автоматически открывать блок;
- предложенный график не должен сам разворачиваться;
- переход к деталям происходит только после явного действия пользователя.

# 3. Core User Journey

Основной MVP-сценарий:

```text
Поиск контрагента
        ↓
Карточка компании
        ↓
Структурированный дашборд
        ↓
Приоритетные сигналы
        ↓
AI summary / suggested questions
        ↓
Вопрос пользователя
        ↓
AI-ответ
        ↓
Evidence / переход в нужный блок
        ↓
Завершение проверки
```

### Критерий завершения Core Journey

Сценарий считается завершённым, когда пользователь:

- получил структурированный отчёт;
- понял основные значимые сигналы;
- при необходимости получил объяснение непонятных данных;
- понимает ограничения доступной информации;
- понимает, достаточно ли ему информации для дальнейших действий.

**Окончательный вердикт о работе / неработе с контрагентом пользователь принимает самостоятельно.**

# 4. Side Journeys

## 4.1. Непонятный индикатор или профессиональный термин

Пользователь видит показатель или сигнал, который не понимает.

Примеры:

- роли истца и ответчика в судебном процессе;
- юридические термины;
- финансовый коэффициент;
- сложный налоговый или регистрационный показатель.

Сценарий:

**отчёт → блок → деталь → понятное объяснение → при необходимости AI-уточнение.**

AI не должен автоматически превращать каждый сложный термин в длинную лекцию.

## 4.2. Недостаточно данных

Пользователь открывает блок, в котором отсутствует необходимая информация.

Показываем:

- явное состояние недостаточности данных;
- какие сведения отсутствуют;
- какие данные всё ещё доступны;
- какие косвенные признаки можно посмотреть;
- какой дополнительный шаг возможен.

## 4.3. Частично заполненный критический блок

Блок в целом содержит данные, но отсутствует критическая информация, необходимая для его корректной оценки.

В этом случае блок **не должен выглядеть заполненным и безопасным только потому, что часть данных присутствует**.

Нужно явно показать:

> данные есть, но их недостаточно для полноценной оценки.

## 4.4. AI не может ответить

Если вопрос пользователя нельзя корректно ответить на основании отчёта:

1. AI сообщает об ограничении;
2. не придумывает отсутствующий факт;
3. объясняет, чего именно не хватает;
4. при наличии релевантных данных предлагает перейти к связанному блоку.

## 4.5. Углубление в конкретный сигнал

**дашборд → блок → детальная информация → AI explanation / evidence → возврат к отчёту.**

# 5. Экран A — Главная / Поиск

## Цель

Минимизировать барьер начала проверки.

## Основные элементы

### Поисковое поле

Пользователь может искать:

- по ИНН;
- по названию компании;
- по ФИО руководителя.

Поиск работает через словарь доступных сущностей.

После выбора конкретной сущности в качестве канонического идентификатора используется ИНН.

### Последние проверки

На первом экране отображаются **три последние проверки** пользователя.

Для каждой:

- название;
- ИНН;
- банковский risk signal;
- дата проверки.

### Избранные компании

Отдельный блок компаний, к которым пользователь хочет быстро возвращаться.

Избранная компания открывает актуальный доступный отчёт.

### Онбординг

Классический onboarding всего продукта не является обязательным.

Основной onboarding относится к AI-чату:

> пользователь должен быстро понять, что в отчёте есть AI, которому можно задавать вопросы по конкретному контрагенту.

Для этого достаточно:

- короткой подсказки;
- примера вопроса;
- нескольких suggested questions.

## Состояния

| Состояние | Поведение |
|---|---|
| Первый визит | Поиск + короткий AI onboarding |
| Есть история | Последние 3 проверки + избранные + поиск |
| Идёт поиск | Inline loading |
| Найдено | Переход к B |
| Не найдено | Inline сообщение, поле остаётся доступным |
| Системная ошибка | Понятное сообщение + повтор |

# 6. Экран A-inline — Результат поиска

## MVP

Поиск выполняется по доступному локальному набору.

Если компания не найдена:

> **«Контрагент не найден в доступном наборе данных»**

Поиск остаётся доступным.

## Future

Fallback во внешние реестры / ЕГРЮЛ.

Сценарий:

**не найдено локально → найдено во внешнем источнике → запрос на обновление → готовый отчёт.**

# 7. Экран B — Дашборд контрагента

## Цель

Дать пользователю быстро считываемую картину состояния контрагента.

## Основной layout

Desktop:

**примерно 60–70% ширины — дашборд**

**примерно 30–40% — AI-chat panel**

По концепции взаимодействия панель чата располагается справа и постоянно доступна во время работы с отчётом.

## Шапка

Показываем:

- название компании;
- ИНН;
- статус компании;
- дату данных;
- **банковский risk signal**.

Банковский signal визуально отделён от локальной оценки значимости блоков.

## Блоки

Основные блоки:

- регистрация;
- финансы;
- судебные дела;
- исполнительные производства;
- реестры;
- деятельность;
- руководство;
- связанные организации.

### Постоянный порядок

Порядок этих блоков одинаков для всех контрагентов.

Это сознательное UX-решение:

> пользователь должен знать, где искать информацию независимо от компании.

### Preview блока

На дашборде блок содержит минимум текста.

Основные элементы:

- название;
- краткие ключевые показатели;
- статус;
- **оценка значимости, сформированная ML/AI-моделью**;
- направление значимости — позитивное, нейтральное или негативное;
- короткий систематизированный комментарий.

Цель preview:

> **пользователь посмотрел → понял значимость блока → решил, нужно ли углубляться.**

# 8. Оценка значимости блока

Для каждого блока на дашборде отображается **оценка потенциальной значимости информации по этому аспекту**.

Оценка формируется ML/AI-моделью на основе доступных данных блока.

Она:

- не заменяет банковский risk signal;
- не является итоговым решением по компании;
- помогает определить приоритет внимания пользователя;
- должна сразу показывать направление сигнала.

### Визуальная модель

Допускается компактная градация:

- **низкая позитивная значимость**;
- **нейтральная значимость**;
- **негативная значимость / требует внимания**;
- **высокая негативная значимость**;
- **недостаточно данных**.

При этом пользователь должен считывать **и силу, и направление** сигнала с первого взгляда.

Конкретные названия уровней и их цветовое кодирование должны быть унифицированы на уровне design system.

### Принцип расчёта

Значимость должна учитывать **содержание и силу сигнала**, а не просто количество негативных признаков.

Ключевой вопрос приоритизации:

> насколько данный набор фактов потенциально важен для способности контрагента выполнять обязательства?

---

# 9. Экран B1 — AI Chat Panel

## Цель

Сделать работу со сложным отчётом понятной через естественный язык.

## Стартовое состояние

При открытии отчёта пользователь видит в чате:

### AI summary

Краткое summary по наиболее существенным моментам.

Summary:

- основано только на отчёте;
- не заменяет банковский risk signal;
- не формирует окончательный вердикт;
- выделяет значимые моменты и ограничения данных.

### Suggested questions

До трёх контекстных вопросов.

Примеры:

- «Что в судебной истории этой компании требует внимания?»
- «Что можно сказать о финансовом состоянии компании по доступным данным?»
- «Каких данных не хватает для более полной оценки?»

Вопросы должны формироваться из текущего состояния конкретного контрагента.

---

# 10. AI Answer

Ответ должен содержать **минимум воды и максимум релевантных данных**.

Основные элементы:

### Краткий вывод

Что пользователь должен понять.

### Факты

Конкретные значения, даты, количества и другие данные.

### Интерпретация

Понятное объяснение значения этих данных.

### Ограничения

Что нельзя утверждать из-за недостатка информации.

### Evidence / переход

Ссылка на соответствующий факт или блок.

---

## Форматы данных в AI-ответе

### Numbers

Числа могут отображаться:

- обычным текстом;
- компактными виджетами;
- небольшими визуальными элементами.

### Graphs

Если ответ ссылается на полноценный график, график предпочтительно не встраивать полностью в чат.

Вместо этого:

**ответ → кнопка / ссылка → нужный блок → конкретный график подсвечивается.**

Таким образом, AI не создаёт отдельную копию отчёта, а помогает пользователю найти нужную часть исходной информации.

---

# 11. AI Evidence

Каждое существенное утверждение должно иметь понятную связь с источником.

В зависимости от типа ответа это может быть:

- конкретное число;
- карточка показателя;
- ссылка на блок;
- ссылка на график;
- дата данных.

### Поведение

AI **не открывает блок автоматически**.

Пользователь сам выбирает:

> **«Открыть блок»**

или другой соответствующий action.

---

# 12. Экран C — Детальный блок

## Назначение

Позволить пользователю глубоко изучить конкретный аспект компании.

### Поведение

При открытии блока он **полностью перекрывает основную область дашборда**.

При этом:

- правый AI chat panel остаётся доступным;
- контекст текущего разговора сохраняется;
- в интерфейсе есть явная стрелка «Назад»;
- пользователь всегда может вернуться к предыдущему состоянию.

На desktop:

**детальный блок занимает основную рабочую область, chat остаётся справа.**

## Структура блока

В верхней части:

### Заголовок

Название блока.

### Description

Краткое объяснение:

> что входит в этот блок и зачем он нужен при проверке контрагента.

### Mini-summary

Справа или в верхней части:

- ключевой статус;
- оценка значимости;
- направление сигнала;
- несколько наиболее значимых показателей.

В основной области:

- детальные сигналы;
- метрики;
- таблицы;
- графики;
- подблоки;
- источники.

---

# 13. AI внутри блока

AI explanation **не является обязательной частью каждого блока по умолчанию**.

Не нужно автоматически превращать каждый экран в учебник по юриспруденции или финансам.

Основной сценарий:

**пользователь задаёт вопрос → AI объясняет конкретный термин / показатель / сигнал.**

При наличии контекстной точки входа интерфейс может предложить пользователю вопросы:

> «Что означает этот показатель?»

> «Почему этот сигнал важен?»

> «Что именно здесь стоит проверить?»

Это сохраняет принцип progressive disclosure.

---

# 14. C-empty / Partial Data

### Полностью пустой блок

Показываем:

**Недостаточно данных для оценки значимости**

и указываем, чего именно не хватает.

### Частично заполненный блок

Если данные есть, но отсутствует критический показатель:

> **Данные представлены частично. Полноценная оценка невозможна, потому что отсутствует X.**

При этом доступные данные продолжают отображаться.

---

# 15. Context & Session Behaviour

AI сохраняет контекст текущего контрагента.

Пользователь может:

- задавать последовательные вопросы;
- уточнять предыдущие ответы;
- переходить между блоками;
- возвращаться к разговору.

При смене контрагента контекст предыдущей компании сбрасывается.

### При открытии блока

Открытие блока:

- **не отправляет сообщение в чат**;
- не изменяет историю;
- не запускает новый AI interaction автоматически.

В чат могут появиться **новые suggested questions**, связанные с открытым блоком.

Это не считается сообщением пользователя или AI.

---

# 16. Feedback

## Feedback на AI-ответ

Под каждым AI-ответом:

**👍 / 👎**

При отрицательном отзыве можно показать компактный набор причин:

- ответ не отвечает на вопрос;
- ответ непонятен;
- недостаточно данных;
- обнаружена ошибка;
- слишком много текста;
- другое.

## Feedback по завершении проверки

После взаимодействия:

> **«Получили ли вы достаточно информации по контрагенту для следующего шага?»**

Варианты:

- Да;
- Частично;
- Нет.

Дополнительно:

> «Что было непонятно или не помогло?»

# 17. Сохранение

Сохранение **не является отдельным экраном**.

## На дашборде

Пользователь может:

- сохранить ссылку на отчёт;
- сохранить / распечатать отчёт в PDF.

Ссылка должна открывать конкретный отчёт.

Дата данных должна быть доступна пользователю.

## В чате

Пользователь может:

- сохранить ссылку на диалог;
- выгрузить диалог в текстовом формате.

Эти действия доступны из соответствующих элементов основного интерфейса.

# 20. Responsive behaviour

## Desktop

Основная модель:

**дашборд 60–70% + AI chat 30–40%.**

При открытии блока:

**детальный блок занимает основную область + AI chat остаётся справа.**

## Mobile

Основной экран — отчёт.

Chat:

- доступен через компактную кнопку / floating entry;
- открывается поверх части интерфейса;
- может перекрывать часть контента, как типичный мобильный chat layer.

При открытии блока:

**блок занимает основной экран и скрывает отчёт.**

Для возврата:

**явная стрелка назад.**

# 22. Content Design

Основной язык интерфейса — понятный предпринимателю без профильной экспертизы.

### Правило

Сначала:

**простое объяснение.**

При необходимости:

**профессиональный термин + краткое пояснение.**

Пример:

> **Ответчик** — компания, к которой предъявлен иск.

Для финансового показателя:

> **Коэффициент текущей ликвидности — 1,24.** Он показывает, насколько доступные оборотные активы покрывают краткосрочные обязательства компании.

Формулировки должны соответствовать фактическому смыслу конкретного показателя.

# 24. UX Acceptance Criteria

## Search

- пользователь понимает, что можно искать по ИНН, названию и ФИО руководителя;
- выбирает нужную компанию;
- понимает ошибку поиска.

## Dashboard

- порядок основных блоков одинаков для всех компаний;
- preview каждого блока считывается быстро;
- ключевые показатели заметны без чтения длинного текста;
- **значимость блока и направление сигнала считываются с первого взгляда**;
- банковский risk signal не путается с ML/AI оценкой значимости блока;
- позитивные, нейтральные, негативные и неизвестные состояния различимы.

## Detail block

- пользователь видит название и назначение блока;
- summary находится в начале блока;
- детальные данные доступны ниже;
- правый chat сохраняется;
- есть явная кнопка «Назад»;
- AI не изменяет chat history без явного действия пользователя.

## AI

- suggested questions релевантны текущему контексту;
- ответ краткий и data-first;
- сложный термин объясняется понятным языком;
- факт и интерпретация различимы;
- существенные утверждения имеют evidence;
- графики открываются через явное действие пользователя;
- при недостатке данных AI не создаёт ложную уверенность;
- feedback доступен под каждым ответом.

## Completion

- пользователь понимает, что основная проверка завершена;
- может зафиксировать отчёт;
- может сохранить ссылку;
- может дать краткую обратную связь.

# 25. UX ↔ Product Alignment

| Product requirement | UX response |
|---|---|
| Быстро понять состояние контрагента | Dashboard + fixed block structure |
| Не читать десятки полей | Compact block previews |
| Понимать значимость сигналов | ML/AI assessment per block + направление сигнала |
| Не перегружаться объёмом данных | Progressive disclosure |
| Разбираться в сложных терминах | Plain-language explanation |
| Доверять AI-ответу | Evidence + links to facts |
| Не заменять решение пользователя | Highlighting, not verdict |
| Не показывать только негатив | Positive / neutral / negative / unknown states |
| Не смешивать компании | Session reset |
| Не менять контекст без пользователя | Explicit action model |
| Не ломать продукт при сбое AI | Independent report + AI error state |
| Возвращаться к знакомой структуре | Fixed block order |
| Работать с большим объёмом данных | Block → sub-block → detail hierarchy |
