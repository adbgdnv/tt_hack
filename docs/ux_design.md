# UX / MVP Design Spec

## 1. Назначение документа

Документ фиксирует, **как продукт выглядит и работает для пользователя на уровне текущего MVP**.

Основная задача UX:

> превратить большой отчёт о контрагенте в понятный интерактивный сценарий, где пользователь быстро видит банковские сигналы, собственный продуктовый разбор, значимые факторы и может задать AI вопрос по тем же данным.

UX поддерживает следующие фактические принципы реализации:

- пользователь не должен собирать картину из десятков полей вручную;
- восемь основных разделов отчёта имеют фиксированный порядок;
- состояние раздела явно различает `SIGNAL`, `FILLED`, `EMPTY` и `NOT_APPLICABLE`;
- банковские оценки отображаются отдельно от собственного вердикта продукта;
- собственный вердикт не является банковским score и рассчитывается детерминированно по уже собранным разделам и весам факторов;
- AI работает с подготовленным отчётом, а не является источником фактов;
- отсутствие данных не трактуется как отсутствие риска;
- пользователь сам инициирует существенные действия: открытие раздела, переход к evidence, отправку вопроса и т. п.;
- контекст сделки хранится отдельно от фактов отчёта и передаётся AI как вводная пользователя.

# 2. UX Principles

## 2.1. From report to understanding

Пользователь не должен читать отчёт последовательно.

Основной путь:

**что важно → какие факты это подтверждают → что это означает → нужно ли углубляться.**

На первом экране сначала видны банковские источники и собственный продуктовый разбор, затем противоречия и восемь разделов проверки.

## 2.2. Progressive disclosure

Большой объём данных раскрывается по уровням:

**summary → block preview → detail → AI explanation / evidence**

Карточка раздела показывает ограниченное количество фактов и факторов. Полный набор данных, графики и пройденные проверки доступны в детальном представлении.

Цель — не скрывать данные, а не выводить весь исходный отчёт одновременно.

## 2.3. Consistent information architecture

Основные разделы и их порядок **не меняются от одного контрагента к другому**:

1. регистрация;
2. финансы;
3. судебные дела;
4. исполнительные производства;
5. реестры;
6. деятельность;
7. руководство;
8. связанные организации.

Меняются значения, состояния, факторы и детализация конкретной компании.

## 2.4. Explainability first

AI отвечает на основе подготовленного отчёта. Существенные утверждения сопровождаются сверкой чисел с отчётом и могут содержать переход к связанному разделу.

AI не должен создавать новый источник данных или выдавать предположение за факт.

## 2.5. No decision substitution

Интерфейс показывает банковский risk signal и отдельный собственный продуктовый вердикт, но не утверждает, что компания «безопасна» или с ней обязательно нужно работать.

Собственный вердикт использует ограниченный словарь:

- **Выглядит чисто**;
- **Уточнить перед сделкой**;
- **Обратить внимание**.

При недостатке данных состояние карточки может быть **«оценить нечем»**. Это не четвёртый уровень риска.

## 2.6. Directional significance

В текущей реализации **нет отдельной ML/AI-оценки значимости каждого блока**.

Значимость и приоритет показываются через:

- состояние раздела (`SIGNAL`, `FILLED`, `EMPTY`, `NOT_APPLICABLE`);
- факторы и их веса;
- визуальное выделение сигнальных разделов;
- собственный вердикт, который выбирается из правил над состояниями и максимальными весами факторов;
- отдельные банковские сигналы.

Поэтому UX не должен описывать эти элементы как результат отдельной модели, если речь идёт о текущем MVP.

## 2.7. Neutral risk framing

Продукт не сводит весь интерфейс к негативным сигналам.

Одновременно различаются:

- наличие сигнала;
- наличие данных без сработавшего сигнала;
- отсутствие данных;
- неприменимость раздела.

Приоритет задаётся не количеством негативных слов, а правилами доменной логики и весами факторов.

## 2.8. Explicit user action

Существенные действия выполняются по явному действию пользователя.

Например:

- AI не открывает раздел автоматически;
- переход к связанному разделу выполняется через action;
- график из AI не создаёт вторую копию графика в чате;
- пользователь сам разворачивает chat и tool blocks.

# 3. Core User Journey

Основной MVP-сценарий:

```text
Поиск контрагента
        ↓
Выбор компании
        ↓
Отчёт
        ↓
Банковские сигналы + собственный вердикт
        ↓
Противоречия и разделы проверки
        ↓
AI summary / suggested questions
        ↓
Вопрос пользователя
        ↓
Streaming AI-ответ
        ↓
Сверка фактов / переход в раздел
        ↓
Следующий шаг пользователя
```

### Критерий завершения Core Journey

Проверка считается содержательно завершённой, когда пользователь:

- открыл отчёт;
- увидел основные сигналы и ограничения данных;
- при необходимости разобрал интересующие разделы;
- получил ответы на дополнительные вопросы;
- понимает, какие факты требуют дальнейшего уточнения.

**Решение о работе с контрагентом остаётся за пользователем.**

# 4. Side Journeys

## 4.1. Непонятный индикатор или профессиональный термин

Пользователь открывает детальный раздел или задаёт AI вопрос о конкретном показателе.

AI объясняет термин и его значение на основании данных отчёта.

## 4.2. Недостаточно данных

Если раздел имеет состояние `EMPTY`, интерфейс явно показывает недостаток данных.

При этом отсутствие данных не превращается в нулевое значение и не считается положительным сигналом.

## 4.3. Частично заполненный критический блок

В отчёте состояние раздела определяется нормализованными данными и серверной логикой. Если раздел не может быть полноценно оценён, это должно оставаться видимым как недостаток покрытия, а доступные факты продолжают отображаться.

## 4.4. AI не может ответить

Если ответ нельзя подтвердить отчётом:

1. AI сообщает об ограничении;
2. не придумывает отсутствующий факт;
3. указывает, каких данных не хватает;
4. при наличии релевантного раздела предлагает перейти к нему.

## 4.5. Углубление в конкретный сигнал

**дашборд → раздел → детали → AI explanation / evidence → возврат к отчёту.**

# 5. Экран A — Главная / Поиск

## Цель

Минимизировать барьер начала проверки.

## Основные элементы

### Поисковое поле

Пользователь может искать:

- по ИНН;
- по названию компании;
- по ФИО руководителя.

Поиск выполняется по доступному набору сущностей. После выбора компании каноническим идентификатором является ИНН.

### Последние проверки

На главном экране отображаются **до трёх последних проверок**, сохранённых в `localStorage` браузера.

Для каждой доступны:

- название;
- ИНН;
- банковский risk signal;
- дата данных.

Это локальная история текущего браузера, а не централизованная история пользователя.

### Избранные компании

Отдельный сценарий избранных компаний **в текущем интерфейсе не реализован**.

### Онбординг

Отдельного обязательного onboarding-flow нет.

Понимание AI достигается через сам chat panel и suggested questions.

## Состояния

| Состояние | Поведение |
|---|---|
| Первый визит | Поиск + пустая история |
| Есть история | До 3 последних проверок + поиск |
| Идёт поиск | Loading у кнопки и inline-индикатор |
| Найдено | Открытие отчёта компании |
| Не найдено | Сообщение об отсутствии компании в доступном наборе |
| Ошибка сервиса | Отдельное сообщение о сбое, без утверждения о компании |

---

# 6. Экран A-inline — Результат поиска

## MVP

Поиск выполняется по доступному локальному набору данных.

Если компания не найдена:

> **«Компании по этому ИНН не существует»**

При этом интерфейс предлагает проверить цифры или ввести другой ИНН.

Ошибки сервиса отделены от результата «не найдено».

## Future

Внешний fallback во внешние реестры / ЕГРЮЛ может быть добавлен позднее, но не является частью текущего search flow.

# 7. Экран B — Дашборд контрагента

## Цель

Дать пользователю быстро считываемую картину по контрагенту и дать доступ к деталям.

## Основной layout

Desktop:

**основная область — отчёт; справа — навигация и AI chat panel.**

Chat располагается в правой колонке и может раскрываться в более крупный режим.

На экране сравнения chat располагается отдельной полосой под сравнением, а не в правой колонке.

## Шапка

Показываем:

- название компании;
- ИНН;
- дату данных, если она получена от сервиса;
- банковский risk signal;
- дополнительные действия: печать / сохранение в PDF и копирование ссылки на отчёт.

Банковский risk signal отделён от собственного вердикта продукта.

## Блоки

Основные блоки:

- регистрация;
- финансы;
- судебные дела;
- исполнительные производства;
- реестры;
- деятельность;
- руководство;
- связанные организации.

### Постоянный порядок

Порядок восьми разделов одинаков для всех контрагентов.

### Preview блока

Карточка раздела показывает:

- название;
- состояние через компактный индикатор;
- до двух ключевых фактов;
- до четырёх наиболее значимых факторов;
- счётчик проверок, если он доступен.

В preview **нет отдельной ML/AI-оценки значимости**. Сигнальность определяется состоянием раздела и факторами.

Цель preview:

> **понять состояние раздела → решить, нужно ли открыть детали.**

# 8. Оценка значимости блока

Для текущего MVP отдельная модель, присваивающая каждому блоку ML/AI score значимости, не используется.

Приоритет визуально выражается комбинацией:

- состояния раздела;
- факторов;
- веса фактора;
- собственного вердикта;
- банковских сигналов, отображаемых отдельно.

### Визуальная модель

Используются четыре состояния данных:

- **SIGNAL** — выявлен значимый сигнал;
- **FILLED** — данные есть, сигнал не сработал;
- **EMPTY** — данных нет;
- **NOT_APPLICABLE** — раздел неприменим.

Собственный вердикт имеет три уровня и отдельное состояние покрытия:

- **Выглядит чисто**;
- **Уточнить перед сделкой**;
- **Обратить внимание**;
- **оценить нечем** — когда «чистый» результат получен при существенных пробелах данных.

### Принцип расчёта

`deriveVerdict` работает над уже подготовленными разделами отчёта.

Верхние факторы для пояснения выбираются по максимальному весу. `attention` получается при наличии тяжёлого сигнального раздела или нескольких сигнальных разделов; один менее тяжёлый сигнал приводит к `clarify`.

Это **правила доменной логики, а не дополнительный ML-score**.

# 9. Экран B1 — AI Chat Panel

## Цель

Позволить задавать вопросы по текущему отчёту и получать объяснение без ручного поиска нужных полей.

## Стартовое состояние

При наличии отчёта chat показывает suggested questions, сформированные из текущего состояния отчёта.

### AI summary

AI-ответы строятся на подготовленном отчёте и истории текущего диалога.

Важное ограничение: **AI не является источником фактов**.

### Suggested questions

Показывается до трёх вопросов одновременно.

Они формируются из:

- условий сделки;
- сигнальных разделов;
- пустых разделов;
- общих вопросов о проверке.

После использования вопрос исключается из видимого набора.

Для сравнения нескольких компаний используются отдельные вопросы, например про отсрочку, различия по финансам и общий уровень внимания.

---

# 10. AI Answer

Ответ поступает в streaming-режиме и отображается как последовательность текстовых и tool-блоков.

Основные элементы:

### Краткий вывод

Основная мысль ответа.

### Факты

Числа, даты и другие сведения из отчёта.

### Интерпретация

Пояснение значения фактов в контексте вопроса.

### Ограничения

Что нельзя утверждать из доступных данных.

### Evidence / переход

При наличии релевантного раздела AI может дать действие для перехода к нему.

После ответа выполняется дополнительная сверка числовых утверждений с отчётом; результат этой сверки отображается пользователю.

---

## Форматы данных в AI-ответе

### Numbers

Числа могут отображаться внутри markdown-ответа и специальных визуальных блоков.

### Graphs

Графики строятся существующим отчётным контуром. В AI tool flow пользователь может получить переход к разделу с соответствующим графиком, а не отдельную вторую версию графика внутри чата.

---

# 11. AI Evidence

AI-ответ связан с исходными данными через:

- числовую сверку утверждений с отчётом;
- указание соответствующего раздела;
- действие перехода к разделу / proof.

### Поведение

AI **не открывает блок автоматически**.

Пользователь сам выбирает действие перехода. При переходе приложение закрывает детальный вид, если он был открыт, и прокручивает страницу к соответствующей карточке.

---

# 12. Экран C — Детальный блок

## Назначение

Позволить пользователю изучить конкретный раздел отчёта.

### Поведение

При открытии раздела он занимает основную рабочую область вместо списка карточек.

При этом:

- правый AI chat panel остаётся доступным;
- история текущего разговора сохраняется;
- есть явная кнопка возврата;
- можно перейти к другим разделам через навигацию.

## Структура блока

В верхней части:

### Заголовок

Название раздела и его состояние.

### Description

Краткое описание того, какие данные входят в раздел и зачем они нужны.

### Mini-summary

Доступны:

- состояние раздела;
- счётчик проверок, если он есть;
- ключевые факты;
- факторы.

В основной области:

- детальные факты;
- факторы и объяснения;
- таблицы;
- графики;
- пройденные проверки;
- источники / связанные данные.

---

# 13. AI внутри блока

AI не встроен как отдельный обязательный компонент каждого раздела.

Основной сценарий:

**пользователь открывает раздел → задаёт вопрос в общем chat → AI объясняет показатель или сигнал.**

Contextual suggested questions могут меняться при открытии раздела, но само открытие раздела не отправляет сообщение в чат.

---

# 14. C-empty / Partial Data

### Полностью пустой блок

Показывается состояние:

**Недостаточно данных для оценки**

или эквивалентная системная подпись состояния.

При этом приложение не подменяет отсутствие данных нулём.

### Частично заполненный блок

Доступные данные продолжают отображаться, а недостаток покрытия не должен интерпретироваться как положительный результат.

Счётчик проверок дополнительно показывает, сколько проверок пройдено, если информация о проверках присутствует в отчёте.

---

# 15. Context & Session Behaviour

AI сохраняет контекст текущего диалога.

Пользователь может:

- задавать последовательные вопросы;
- уточнять предыдущие ответы;
- переходить между разделами;
- возвращаться к разговору в рамках текущего сеанса.

При смене контрагента история AI очищается.

При смене состава пула сравнения история разбора пула также очищается.

### Контекст сделки

В chat есть отдельная панель условий сделки. Поддерживаются:

- сторона контрагента: поставщик / покупатель;
- схема расчётов: аванс / отсрочка / оплата по факту;
- сумма;
- срок;
- цель.

Условия могут задаваться как в отдельной панели, так и в тексте вопроса. Они считаются **словами пользователя**, а не фактами отчёта.

При смене компании контекст сделки сохраняется, поскольку относится к задаче пользователя, а не к самой компании.

### При открытии блока

Открытие блока:

- не отправляет сообщение в чат;
- не изменяет историю сообщений;
- не запускает новый AI interaction автоматически.

# 16. Feedback

## Feedback на AI-ответ

Под AI-ответом доступны:

**👍 / 👎**

При отрицательной оценке показываются причины:

- Не отвечает на вопрос;
- Непонятно;
- Недостаточно данных;
- Обнаружена ошибка;
- Слишком много текста;
- Другое.

В текущем MVP feedback хранится в состоянии текущего клиента и **не отправляется в централизованную product analytics систему**.

## Feedback по завершении проверки

После отчёта доступен короткий completion-feedback с вопросом, получил ли пользователь достаточно информации для следующего шага.

Ответ показывается через UI feedback / toast, но централизованная аналитика этого события в MVP не реализована.

---

# 17. Сохранение

Сохранение **не является отдельным экраном**.

## На дашборде

В текущем интерфейсе доступны:

- печать / сохранение отчёта через браузерный print flow;
- копирование ссылки на конкретный отчёт по ИНН.

URL содержит ИНН и при открытии повторно загружает соответствующий отчёт.

Дата данных показывается в шапке, если она получена от сервиса.

## В чате

Отдельные действия сохранения / экспорта диалога **в текущем MVP не являются реализованным пользовательским flow**.

# 18. Comparison

Сравнение нескольких контрагентов **реализовано в текущем MVP**.

Пользователь переключается в режим «Сравнение контрагентов» и формирует пул компаний.

Сервер возвращает сравнение по единому набору признаков. Результат не является числовым рейтингом: он содержит вердикты, причины и рекомендации по порядку внимания.

AI в режиме сравнения работает с пулом компаний. Для него используются отдельные group-level suggested questions.

# 20. Responsive behaviour

## Desktop

Для отчёта используется двухколоночная модель:

**основная область отчёта + правая колонка AI / навигации.**

При открытии детального раздела он занимает основную область, а AI остаётся справа.

В режиме сравнения AI располагается под основным сравнением.

## Mobile

Мобильный layout адаптирует отчёт и chat под узкую ширину.

Chat может открываться как отдельный слой поверх основного контента.

При открытии детального раздела основной контент переключается на выбранный раздел; возврат выполняется явным действием.

# 21. Loading / Error States

### Loading

Скелетоны соответствующей области.

### Empty

Раздел существует, но данных для него нет.

### Partial

Доступна часть данных; интерфейс не должен выдавать её за полную оценку.

### Not applicable

Раздел неприменим.

### Error

Техническая ошибка отделена от состояния данных компании.

### AI unavailable

Отчёт продолжает работать независимо от AI.

При ошибке AI показывается отдельное сообщение о недоступности разбора, а данные отчёта остаются доступны.

# 22. Content Design

Основной язык интерфейса — понятный предпринимателю без профильной экспертизы.

### Правило

Сначала:

**что произошло / какие данные есть.**

Затем:

**что это может означать и что проверить дальше.**

Термины объясняются простым языком, но формулировка должна соответствовать фактическому смыслу конкретного поля или фактора.

# 23. Future Interaction Concepts

Следующие направления могут развивать MVP, но не должны описываться как уже реализованные:

### Search enrichment

- внешний fallback / ЕГРЮЛ;

Отслеживание изменений между временными срезами.

### Advanced visual analytics

Дополнительные аналитические представления поверх уже доступных данных.

# 24. UX Acceptance Criteria

## Search

- пользователь понимает, что можно искать по ИНН, названию и ФИО руководителя;
- выбирает нужную компанию из доступных результатов;
- различает «не найдено» и технический сбой.

## Dashboard

- порядок восьми основных разделов одинаков для всех компаний;
- preview каждого раздела считывается быстро;
- ключевые факты заметны без чтения всего текста;
- `SIGNAL`, `FILLED`, `EMPTY` и `NOT_APPLICABLE` различимы;
- банковский risk signal не путается с собственным вердиктом;
- отсутствие данных не выглядит как положительный результат;
- противоречия отображаются отдельно, если они присутствуют в серверном отчёте.

## Detail block

- пользователь видит название и состояние раздела;
- описание и ключевые факты находятся в начале;
- детальные данные доступны ниже;
- AI остаётся доступен;
- есть явное действие возврата;
- открытие раздела не создаёт сообщение в chat.

## AI

- suggested questions соответствуют текущему отчёту / сделке / пулу;
- ответ основан на доступном отчёте;
- сложные показатели объясняются понятным языком;
- факт не смешивается с пользовательской вводной;
- числовые утверждения проходят сверку с отчётом;
- AI не создаёт ложную уверенность при недостатке данных;
- feedback доступен под ответом;
- streaming не ломает возможность продолжить диалог.

## Comparison

- пользователь может собрать пул контрагентов;
- сравнение строится по единому набору признаков;
- результат не маскируется под числовой score;
- AI понимает, что вопрос относится к группе компаний.

## Completion

- пользователь может вернуться к отчёту по ссылке;
- может распечатать / сохранить отчёт через браузерный print flow;
- может дать feedback по AI и завершению проверки.

# 25. UX ↔ Product Alignment

| Product requirement | UX response |
|---|---|
| Быстро понять состояние контрагента | Банковские сигналы + собственный вердикт + triggers + фиксированные разделы |
| Не читать десятки полей | Compact block previews |
| Понимать приоритет сигналов | Состояния разделов + факторы + веса + собственный вердикт |
| Не перегружаться объёмом данных | Progressive disclosure |
| Разбираться в сложных терминах | AI explanation по запросу |
| Доверять AI-ответу | Числовая сверка + переход к разделу / evidence |
| Не заменять решение пользователя | Банковский signal и собственный вердикт явно разделены; финальное решение не автоматизируется |
| Не показывать только негатив | `SIGNAL` / `FILLED` / `EMPTY` / `NOT_APPLICABLE` |
| Не смешивать компании | Сброс истории при смене компании / состава пула |
| Не менять контекст без пользователя | Явные действия для открытия разделов, отправки вопросов и переходов |
| Не ломать продукт при сбое AI | Отчёт работает независимо от AI |
| Возвращаться к знакомой структуре | Фиксированный порядок восьми разделов |
| Работать с большим объёмом данных | Preview → detail → facts / factors / charts / checks |
| Учитывать задачу конкретной сделки | Отдельный контекст сделки, который передаётся AI как вводная пользователя |
| Сравнивать несколько компаний | Отдельный реализованный режим Comparison без числового рейтинга |
